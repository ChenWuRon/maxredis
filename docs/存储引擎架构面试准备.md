### 1.4 为什么这样设计

1. **分片 + 线程绑定**：每个 CPU 核心处理自己的 Shard，数据无锁访问，零竞争
2. **Fiber 协程**：每个连接一个 fiber，轻量（64KB 栈），数万连接无压力
3. **io_uring**：批量提交 I/O 请求，一次系统调用完成的 I/O 操作比 epoll 多
4. **读写分离**：读不经过 Raft，延迟更低
5. **单节点 FastCommitPath**：没有 peer 时 Append→Commit→Apply 三步同步完成，无网络开销

## 二、Sharded Storage

### 2.1 为什么要分片

**核心问题**：单线程 Redis 只能用一个 CPU 核心，QPS 受限于单核能力。

**分片解决**：数据按 key 分到 N 个 CPU 核心，每个核心独立处理自己的分片。N 个核心 → 理论 N 倍吞吐。

```
不分片：                   分片 (N=4)：
  ┌─────────┐               Thread 0    Thread 1    Thread 2    Thread 3
  │ 所有key  │               keys A-F    keys G-M    keys N-T    keys U-Z
  │  单核处理 │               ───────     ───────     ───────     ───────
  └─────────┘               无锁访问     无锁访问     无锁访问     无锁访问
  1x 吞吐                   4x 吞吐
```

### 2.2 Key 如何路由到 Shard

```cpp
// storage/common_types.h:47-50
template <typename View>
inline ShardId Shard(const View& v, ShardId shard_num) {
  XXH64_hash_t hash = XXH64(v.data(), v.size(), 120577);
  return hash % shard_num;
}
```

**流程**：
1. 用 `XXH64`（极快的非加密 hash）计算 key 的 hash 值
2. `hash % shard_num` 得到分片 ID
3. 后续所有对该 key 的操作都投递到该分片对应的线程

### 2.3 为什么相同 Key 进入同一个 Shard

因为在 hash 函数不变的情况下，`XXH64("a") % N` 恒等于同一个值。

这保证了：
- 同一个 key 的所有操作（SET → GET → DEL）都在同一个分片线程中执行
- **串行化**：对该 key 的操作天然串行，无需分布式锁
- **一致性**：Raft 的 `ApplyLogEntry` 在一条日志被 commit 后，按 index 顺序执行，到达分片线程后按 `FiberQueue` 的 FIFO 顺序处理

### 2.4 为什么不同 Shard 可以并行

- 线程 0 处理 Shard 0 的 key（如 "aaa"）
- 线程 1 处理 Shard 1 的 key（如 "bbb"）

两个操作访问不同的 `flat_hash_map`（在不同线程的内存空间中），完全无交集。“aaa”的 SET 和“bbb”的 GET 可以同时在两个不同 CPU 核心上执行。

### 2.5 为什么几乎不用加锁

```cpp
// engine_shard_set.h:31-33
class EngineShard {
  DbSlice db_slice;                          // 只被本线程访问
  static thread_local EngineShard* shard_;    // thread_local 单例
};
```

关键设计：
1. 每个 `EngineShard` 是 `thread_local` 的，只在本线程创建和访问
2. `DbSlice` 内部的 `flat_hash_map` 只有本线程能访问，不需要 mutex
3. 跨线程访问通过 **消息传递**：`shard_set_->Await(sid, lambda)` 把任务投递到目标线程的 `FiberQueue`，目标线程执行完再返回

```cpp
// kv_state_machine.cc:53-57
void KvStateMachine::Set(DbIndex db_ind, string_view key, string_view val) {
  ShardId sid = Shard(key);  // 计算目标分片
  shard_set_->Await(sid, [db_ind, key, val] {
    EngineShard* es = EngineShard::tlocal();   // 在目标线程执行
    auto [it, res] = es->db_slice.AddOrFind(db_ind, key);
    it->second.value = val;
  });
}
```

**这里的关键**：`Await` 将 lambda 序列化到目标线程执行，调用者 fiber 挂起等待结果。数据本身不跨线程共享，只有 lambda 闭包传递。

### 2.6 EngineShardSet 和 DbSlice 源码解析

```cpp
// engine_shard_set.h:59-96
class EngineShardSet {
  util::ProactorPool* pp_;
  vector<FiberQueue*> shard_queue_;  // 每个分片一个 FiberQueue

  // 跨线程投递 + 同步等待结果
  template <typename F> auto Await(ShardId sid, F&& f) {
    return shard_queue_[sid]->Await(forward<F>(f));
  }

  // 跨线程投递，不等待
  template <typename F> auto Add(ShardId sid, F&& f) {
    return shard_queue_[sid]->Add(forward<F>(f));
  }

  // 所有分片并行执行
  template <typename U> void RunBriefInParallel(U&& func) {
    BlockingCounter bc{size()};
    for (uint32_t i = 0; i < size(); ++i) {
      pp_->at(i)->DispatchBrief([f = func, bc]() mutable {
        f(EngineShard::tlocal());
        bc->Dec();
      });
    }
    bc->Wait();  // 等待所有分片完成
  }
};
```

```cpp
// engine_shard_set.cc:28-33
EngineShard::EngineShard(ShardId index)
    : db_slice(index, this), queue_(kQueueLen) {
  fiber_q_ = fb2::Fiber("shard_queue" + index, [this] {
    queue_.Run();  // 启动 FiberQueue 的处理 fiber
  });
}
```

每个 `EngineShard` 内部有一个 `FiberQueue`（MPSC 队列）和对应的处理 fiber。外部线程 `Await(sid, task)` 时，task 被 push 到队列，处理 fiber 取出执行，把结果传回调用者。

```cpp
// db_slice.cc:42-64
auto DbSlice::Find(DbIndex db_index, string_view key) -> OpResult<MainIterator> {
  auto& db = db_arr_[db_index];
  MainIterator it = db.main_table->find(key);           // flat_hash_map::find
  if (it == db.main_table->end()) {
    return OpStatus::KEY_NOTFOUND;
  }
  // 检查过期
  if (it->second.expire_ms != 0 && it->second.expire_ms <= NowMs()) {
    db.stats.obj_memory_usage -= (it->first.capacity() + it->second.value.capacity());
    db.main_table->erase(it);
    return OpStatus::KEY_NOTFOUND;
  }
  return it;
}
```

**面试回答模板**：

> 我们采用 key-hash 分片架构，用 XXH64 对 key 做 hash 然后模分片数确定目标分片。每个分片绑定到一个 proactor 线程，拥有独立的 `flat_hash_map`，访问完全无锁。跨线程通过 `FiberQueue` 消息传递，`Await(sid, lambda)` 把任务投递到目标线程，调用者 fiber 挂起等待结果。同一 key 的所有操作都在同一分片串行执行，天然保证一致性。

## 三、Fiber 调度

### 3.1 Fiber 原理

Fiber 是**用户态协程**，基于 `boost.context` 的 `jump_fcontext` 实现栈切换。

```cpp
// helio/util/fibers/fibers.h:15-70
class Fiber {
  // 默认栈大小 64KB（线程栈是 8MB）
  struct Opts {
    Launch launch = Launch::post;
    FiberPriority priority = FiberPriority::NORMAL;
    string name;
    uint32_t stack_size = 64 * 1024;  // ← 轻量！
  };
  
  template <typename Fn>
  Fiber(string_view name, Fn&& fn)  // 创建一个 fiber 执行 fn
    : impl_{MakeWorkerFiberImpl(name, fn)} { Start(Launch::post); }
};
```

### 3.2 Fiber vs 线程 vs 系统协程

| | Thread | 系统协程 (goroutine) | Fiber (boost.context) |
|------|------|------|------|
| 栈大小 | 8MB (固定) | 2KB 起步，可增长 | 64KB (固定) |
| 切换开销 | ~1-2us (内核态) | ~200ns | ~50ns (纯用户态) |
| 调度者 | OS 内核 | Go Runtime | 项目自己的 Scheduler |
| 并发数 | 数千 | 数十万 | 数万 |
| 切换时机 | 抢占式 | 抢占+协作 | 协作式 (SleepFor/Yield) |
| 内存开销 | 大 | 小 | 极小 |

**为什么 Fiber 切换快**：
- 纯用户态，不陷入内核
- 只保存/恢复 callee-saved 寄存器 + 栈指针（~16 个寄存器）
- `jump_fcontext` 是手写汇编，极快

### 3.3 项目中的 Fiber 实例

#### 3.3.1 InputLoop Fiber（每个连接一个）

```cpp
// dragonfly_connection.cc:175
void Connection::InputLoop(FiberSocketBase* peer) {
  do {
    DoRead(peer, RecvNotification{}, &io_buf);    // io_uring/epoll 异步读
    evc_.await([&] {                              // fiber 挂起等待数据
      return io_buf.InputLen() > min_parse_threshold || ec_;
    });
    ParseRedis(&io_buf);                          // 解析 RESP
    service_->DispatchCommand(...);                // 分发执行
    cc_->ReplyReadyCommands();                     // 写回响应
  } while (peer->IsOpen());
}
```

#### 3.3.2 Heartbeat Fiber（Leader 专用）

```cpp
// raft_node.cc:373-409
void RaftNode::HeartbeatLoop() {
  while (!shutdown_ && role_ == RaftRole::Leader) {
    SendHeartbeatToPeers();        // 向所有 peer 发心跳
    ExtendLeaderLease();           // 刷新 leader 租约
    // leader transfer 超时检查...
    ThisFiber::SleepFor(50ms);     // fiber 睡眠 50ms（不阻塞线程！）
  }
}
```

**启动**：`BecomeLeader()` 时 `heartbeat_fiber_ = Fiber("heartbeat", [this] { HeartbeatLoop(); })`
**停止**：角色变为 Follower/Candidate 时调用 `StopHeartbeat()`

#### 3.3.3 Election Fiber（Follower 专用）

```cpp
// election_timer.cc
void ElectionTimer::Run() {
  while (!shutdown_) {
    int timeout_ms = dist_(rng_);  // 随机 150~300ms（Raft 论文要求）
    ThisFiber::SleepFor(milliseconds(timeout_ms));
    // 如果 SleepFor 期间被 Reset() 过，epoch 会变化，跳过
    if (epoch_.load() != saved) continue;
    active_.store(false);
    if (cb_) cb_();  // 触发 OnElectionTimeout → BecomeCandidate
  }
}
```

**关键设计**：
- `Reset()` 递增 `epoch_` 计数器——如果在 sleep 期间收到了合法心跳，唤醒后检测到 epoch 变化，重新开始计时
- `Deactivate()` 暂停计时但不停止 fiber，避免频繁创建销毁
- `dist_{150, 300}` 随机间隔避免多个 follower 同时发起选举（split vote）

#### 3.3.4 Snapshot Fiber

```cpp
// snapshot_fiber.cc
void SnapshotFiber::Run() {
  while (!shutdown_) {
    uint64_t now = NowMs();
    bool time_trigger = (now - last_snapshot_time_ms_) >= time_threshold_sec_ * 1000;
    bool cmd_trigger = write_count_ >= cmd_threshold_;
    if (time_trigger || cmd_trigger) {
      service_->CreateSnapshot();  // 触发快照
      last_snapshot_time_ms_ = now;
      write_count_ = 0;
    }
    ThisFiber::SleepFor(1s);  // 每秒检查一次
  }
}
```

`NotifyWrite()` 被 `Service::Set/Del/Expire` 调用，递增原子计数器 `write_count_`。

### 3.4 EngineShard::Await() 实现原理

```cpp
// engine_shard_set.h:55-58
template <typename F>
auto EngineShardSet::Await(ShardId sid, F&& f) {
  return shard_queue_[sid]->Await(std::forward<F>(f));
}
```

`shard_queue_[sid]` 是目标分片的 `FiberQueue`。`Await` 将 lambda 推入队列：
1. 目标线程的 `FiberQueue::Run()` fiber 从队列取出 lambda 执行
2. 执行完成后，通过 `Done`/`EventCount` 唤醒调用方 fiber
3. 调用方 fiber 拿到返回值，继续执行

```
调用者线程 (Thread 0)              目标线程 (Thread 3, Shard 3)
     │                                     │
     │ Await(sid=3, lambda) ─────────────► │
     │ (fiber挂起)                          │ FiberQueue::Run()
     │                                     │ 取出lambda执行
     │                                     │ lambda(begin,end)
     │                                     │ Done::Notify()
     │ ◄──── 唤醒 ─────────────────────── │
     │ 拿到返回值                            │
     ▼                                     ▼
```

### 3.5 为什么 Fiber 适合 KV 系统

1. **高并发连接**：每个连接一个 fiber（64KB），内存开销远小于每连接一线程（8MB）
2. **I/O 密集**：Fiber 在 I/O 等待时 `SleepFor`/`await` 不阻塞线程，线程可以处理其他 fiber
3. **协作式调度**：没有抢占开销，适合短任务（SET/GET 都是微秒级）
4. **无锁同步**：`EventCount`、`Done`、`Mutex` 都是 fiber 友好的，阻塞只让出 CPU 不阻塞线程
5. **定时任务**：Heartbeat（50ms）、Election（150-300ms）、Snapshot（1s）都是 fiber `SleepFor`，不占线程资源

**面试回答模板**：

> 我们基于 boost.context 实现了用户态 Fiber，默认栈只有 64KB，切换成本 ~50ns，纯用户态不进入内核。每个 TCP 连接一个 Fiber 处理 InputLoop，通过 `evc_.await` 挂起等待 I/O 事件。Raft 的选举定时器和心跳都是独立 Fiber，用 `SleepFor` 实现非阻塞等待。跨分片通过 `FiberQueue::Await` 投递任务，目标线程执行完成后用 EventCount 唤醒调用方 Fiber。这套机制的核心优势是：数万连接共享少量线程，I/O 等待不浪费 CPU，协作式调度没有抢占开销。

## 四、io_uring

### 4.1 Linux 传统 I/O 模型

```
应用程序                    内核
  write(fd, buf, len)  ───►  拷贝数据到内核缓冲区
    (阻塞/返回)        ◄───   内核调度磁盘/网络
                       
  问题：
  - 每次 I/O 都是一次系统调用 (syscall)，用户态↔内核态切换有开销
  - epoll 需要两次系统调用：epoll_wait() + read()，each event = 2 syscalls
```

### 4.2 epoll 的问题

```
epoll 模型：
  epoll_wait(efd, events, MAXEVENTS, timeout)  ← syscall 1
  for each event:
    read(fd, buf, len)                          ← syscall 2 (per event)
    process(buf)

1万个事件 = 10001 次系统调用
```

### 4.3 io_uring 优势

```
io_uring 模型：
  ┌──────────────────────┐
  │   Submission Queue   │  (SQ)  用户→内核，共享内存，无 syscall 写入
  │   [sqe1][sqe2]...   │
  └──────────────────────┘
            │
    io_uring_enter()  ← 批量提交（仅在需要时调用一次 syscall）
            │
  ┌──────────────────────┐
  │  Completion Queue    │  (CQ)  内核→用户，共享内存
  │  [cqe1][cqe2]...    │
  └──────────────────────┘

1万个事件 = 可能只需 1 次 io_uring_enter() + 1 次大的批量处理
```

**核心优势**：
1. **批量提交**：多个 SQEs 一次 `io_uring_enter()` 提交给内核
2. **批量收割**：一次 `io_uring_wait_cqes()` 收割多个完成的 CQEs
3. **零拷贝**：共享内存做 SQ/CQ 环形缓冲区，无数据拷贝
4. **Fixed buffers/files**：预注册内存和文件描述符，减少每次操作的内核处理
5. **SQ poll**：内核主动轮询 SQ，不需要系统调用

### 4.4 SQ/CQ 工作流程

```
用户程序:
  1. io_uring_get_sqe(ring) → 获取空闲 SQE
  2. io_uring_prep_readv(sqe, fd, iovecs, nr_vecs, offset)  ← 填入操作
  3. io_uring_submit(ring) → 提交所有 SQE，可能无 syscall
  ... 处理其他事情 ...
  4. io_uring_wait_cqes(ring, &cqes, count, ...) → 收割完成的 CQE
  5. 处理每个 cqe->res (返回值)
  6. io_uring_cqe_seen(ring, cqe) → 标记已消费
```

### 4.5 为什么减少 syscall 和 context switch

| | epoll | io_uring |
|------|------|------|
| 每个 accept | 1 syscall | 可能 0（SQ poll） |
| 每个 read | 1 syscall | 可能 0（SQ poll 或 batch） |
| 每个 write | 1 syscall | 可能 0 |
| 上下文切换 | 每次 syscall 都切换 | 批量处理，次数少几十倍 |
| 内存拷贝 | read 从内核拷贝到用户缓冲区 | Fixed buffers 省去一次拷贝 |

### 5.2 为什么 absl::flat_hash_map 比 std::unordered_map 更好

| | `std::unordered_map` | `absl::flat_hash_map` |
|------|------|------|
| 底层结构 | 分离链地址法（链表桶） | 开放寻址（open addressing） |
| 内存布局 | 节点分散在堆上 | 连续数组存储 |
| Cache Miss | 严重（追踪指针） | 少（线性探测） |
| 插入开销 | malloc + 链表操作 | 数组插入（可能触发 rehash） |
| 查找开销 | 链表遍历 | 线性探测 + SIMD 优化 |
| 迭代速度 | 慢（链表遍历） | 快（数组遍历） |
| 删除 | O(1) 链表操作 | Tombstone 标记 |

### 5.3 Swiss Table 原理（absl::flat_hash_map 的实现）

Swiss Table 是 Google 在 Abseil 中实现的 hash 表，核心设计：

1. **元数据与控制分离**：用一个单独的 `ctrl_` 数组存储每个槽位的状态（EMPTY/DELETED/低7位 hash），用 SIMD 一次比较 16 个槽位的 hash
2. **SSE2/NEON 加速探测**：`_mm_cmpeq_epi8` 一次比较 16 个字节，快速找到候选槽位
3. **连续内存**：所有条目存储在连续的堆数组上，对 CPU cache 友好
4. **负载因子**：默认 `7/8 = 87.5%`（vs std::unordered_map 的 ~70%）

```
Swiss Table 内存布局:

  ctrl_[0..15]   slots[0..15]
  ┌──────────┐   ┌──────────────┐
  │H|E|D|H|.. │   │k1|v1|k2|v2|..│  ← 连续内存
  └──────────┘   └──────────────┘
  SSE2一次比较16个ctrl

查找流程:
  1. hash(key) → H1(高位), H2(低7位)
  2. SSE2对比 ctrl_ 中所有等于 H2 的位置
  3. 对每个候选位置，比较完整 key
```

### 5.4 Cache Locality

传统 `std::unordered_map`（分离链地址法）：

```
bucket[0] → node1 → node2 → node3
  │          (heap)  (heap)  (heap)
  │          ↑ cache miss  ↑ cache miss
```

Swiss Table（开放寻址）：

```
slots[0..N]:  ←──── 连续内存 ────→
  [k,v][k,v][k,v][k,v][k,v]...[k,v]
  
CPU 一次加载一个 cache line (64B) 可以包含 3-4 个 entry
```

对于 KV 系统来说：
- **GET 操作**就是一次 `flat_hash_map::find(key)`，大部分情况在 1-2 次探测内命中
- **SET 操作**是一次 `emplace`，可能触发 rehash（扩容），但 Swiss Table 的 load factor 高，rehash 频率低
- 连续迭代（`Traverse`）是顺序扫描数组，对 CPU prefetch 友好

### 5.5 为什么 GET 性能更高

1. **读不经过 Raft**：直接 `Schedule` 到分片线程 → `DbSlice::Find`
2. **无锁**：分片线程单线程访问 `flat_hash_map`
3. **hash 表查找极快**：Swiss Table 的 SIMD 加速探测
4. **无磁盘 I/O**：纯内存操作
5. **零拷贝**：`Find` 返回 `MainIterator`，value 直接引用 hash 表中的 `string`

### 5.6 数据写入流程（SET 为例）

```
Client: SET a 1
  → ParseMultiBulk: tokens=["SET","a","1"]
  → DispatchCommand → registry_["SET"] → Service::Set
  → RaftEngine::SubmitCommand(cid, args)
  → CommandEncoder::Encode → ReplicatedCommand{SET, ["SET","a","1"]}
  → 单节点: FastCommitPath
    → LogEntry → Append → AdvanceCommitIndex(0→1) → ApplyCommittedLogs
    → KvStateMachine::ApplyLogEntry("SET a 1")
    → Shard("a") → shard_set_->Await(sid=hash("a")%N, lambda)
    → EngineShard::tlocal()->db_slice.AddOrFind(0, "a")
      → db.main_table->emplace("a", MainValue{})    ← 插入hash表
      → it->second.value = "1"                      ← 设置值
  → ReplyBuilder::SendStored() → "+OK\r\n"
```

**面试回答模板**：

> 存储引擎的核心是 per-shard 的 `absl::flat_hash_map`。选择 Abseil 的 Swiss Table 而不是 `std::unordered_map`，是因为开放寻址 + 连续内存布局对 CPU cache 更友好，SSE2 SIMD 一次比较 16 个槽位的 hash。过期处理用懒惰删除——Find 时检查 expire_ms，过期直接 erase。写入走 Raft 共识路径，Apply 阶段通过 `Await(sid)` 跨线程投递到目标分片，在目标线程内无锁操作 hash 表。

## 七、性能优化

### 7.1 Sharding — 水平扩展

```
不分片 (单线程):              分片 (N=4):
  1 CPU 核心, 1 hash_map      4 CPU 核心, 4 hash_map
  QPS = 1x                     QPS = 理论 4x

收益：
  - 不同 key 的操作在不同核心并行处理
  - 每个核心独立的 L1/L2 cache，cache 命中率更高
  - 无锁竞争，无 false sharing
```

### 7.2 Fiber — 高并发低成本

```
Thread 模型:                     Fiber 模型:
  1万个连接 = 1万个线程            1万个连接 = 1万个 fiber (4个线程)
  内存: 10000 × 8MB = 80GB       内存: 10000 × 64KB = 640MB
  上下文切换: 内核调度, ~1us        上下文切换: 用户态 jmp, ~50ns
  I/O 模型: 线程阻塞               I/O 模型: fiber 挂起，线程继续工作
```

### 7.3 io_uring — 减少系统调用

```
epoll:                            io_uring:
  每个 I/O: syscall × 2            每个 batch: syscall × 1 (或 0)
  1万事件 ≈ 20001 syscalls        1万事件 ≈ 1-3 syscalls
  每次 syscall: ~100ns overhead   批量处理, overhead 分摊
```

### 7.4 absl::flat_hash_map — Cache 友好

```
std::unordered_map:                 absl::flat_hash_map:
  bucket → node → node (链表)       连续数组 [k,v][k,v]...
  每次查找: 追指针, cache miss 多    每次查找: 连续探测, cache hit 高
  SSE 加速: 无                      SSE2: 一次比较 16 个槽
  Load factor: ~70%                 Load factor: 87.5% (= 更省内存)
```

### 7.5 零拷贝

| 阶段 | 传统做法 | 项目做法 |
|------|------|------|
| RESP 解析 | 拷贝到新 buffer | `bulk_str = str.subspan(0, len)` (引用 IoBuf) |
| 参数传递 | 拷贝到 `vector<string>` | `CmdArgList = Span<MutableStrSpan>` (引用原数据) |
| 响应发送 | `sprintf` + `write` | `writev` gather-scatter 多段发送 |
| 跨线程投递 | 拷贝参数 | lambda 闭包捕获，移动语义 |

### 7.6 读写分离

不考虑 Raft 去处理读请求：
- 读请求不产生 Raft 日志
- 读请求不等待多数派
- `commit_index` 不变化
- P99 延迟更低（不需要等复制）

**面试回答模板**：

> 性能优化主要体现在四个维度：① 分片水平扩展——key hash 到多个 CPU 核心并行处理，无锁；② Fiber 轻量并发——64KB 栈，数万连接共享少量线程；③ io_uring 批量 I/O——系统调用数降低 1-2 个数量级，零拷贝 buffer ring；④ Swiss Table 存储——开放寻址 + SIMD 加速探测，连续内存对 CPU cache 友好。单机环境下 GET 延迟在微秒级，SET 单节点走 FastCommitPath，只有 Append+Commit+Apply 三步，没有网络开销。

**面试可用数据**：

| 指标 | 数据 | 说明 |
|------|------|------|
| SET QPS | **~39K** | 单连接串行，Raft FastCommitPath |
| SET P50 延迟 | **25us** | Append+Commit+Apply 全路径 |
| SET P99 延迟 | **54us** | 极端情况仍 < 100us |
| GET QPS | **~19K** | 单连接串行（受 Python 客户端影响） |
| GET P50 延迟 | **49us** | DbSlice hash 查找 |
| Pipeline x64 GET | **631K QPS** | 服务端真实吞吐上限 |
| PING QPS | **~40K** | 纯 RESP 解析+编码路径 |

**GET 为什么比 SET 慢？**

> GET 走的是异步调度路径：`Service::Get` 通过 `engine_.Schedule(key, cb)` 把回调投递到分片线程的 `FiberQueue`，然后直接返回。响应要等分片线程 fiber 取出任务 → 执行 `DbSlice::Find` → 调用 `SendGetReply` 才写入 socket。比 SET 多了一次跨 fiber 调度。SET 全程在同一个 fiber 调用栈内同步完成。
>
> Pipeline 掩盖了这次调度的开销——Pipeline x64 下调度延迟被 64 条命令平摊，达到 631K QPS，这才是服务端的真实处理能力。

**面试回答模板**：

> 我们在 2 核虚拟机上跑了一次单连接 TCP 基准测试。SET 达到约 4 万 QPS，P50 延迟 25 微秒，P99 控制在 54 微秒以内——这包含了 RESP 解析、Raft FastCommitPath（Append+Commit+Apply）、DbSlice 写入、RESP 编码的全路径。GET 因为是异步调度到分片线程，单连接约 2 万 QPS。Pipeline 64 压到 63 万 QPS，证明服务端 CPU 处理能力远未饱和，瓶颈在 Python 客户端串行 round-trip。另外我们有 32 个测试文件，覆盖了 Raft 协议的完整测试：节点角色转换、选举超时、日志复制、冲突解决、快照创建传输和应用、WAL 持久化和恢复、分段日志管理等。

## 十、项目介绍

### ① 一分钟项目介绍（电梯 pitch）

> 我基于 C++ 17 从零实现了一个兼容 Redis RESP 协议的分布式 KV 存储。核心架构是三件事：① 多线程 key-hash 分片，每个分片一个 lock-free 的 Swiss Table，数据按 key 路由到不同 CPU 核心并行处理；② 用 Fiber 协程替代线程处理连接，64KB 栈，io_uring 批量 I/O，系统调用减少 1-2 个数量级；③ 自研了完整的 Raft 共识协议，支持选举、日志复制、快照、成员变更等，32 个测试覆盖了正常路径和故障恢复。实测数据：SET 约 4 万 QPS/P50=25us/P99=54us，Pipeline 64 达到 63 万 QPS。

### ② 三分钟项目介绍

> 我做的这个项目是一个兼容 Redis RESP 协议的高性能分布式 KV 存储。它的核心存储架构和 Redis 完全不同——不是单线程模型，而是多线程分片架构。
>
> 架构上最核心的是三层：
>
> **存储层**——数据按 key 做 XXH64 hash 然后分片到多个 CPU 核心，每个分片绑定一个线程，内部用 `absl::flat_hash_map`（Swiss Table）存储数据。同一线程访问本分片数据完全无锁，不同分片在不同线程上并行处理。跨线程通过 `FiberQueue` 消息传递——`Await(sid, task)` 把任务投递到目标线程，执行完后唤醒调用方 fiber。
>
> **网络和调度层**——每个 TCP 连接一个 Fiber 协程处理，默认栈只有 64KB。I/O 底层用 io_uring 替代 epoll，批量提交 SQE、批量收割 CQE，系统调用数降低一个数量级。`UringProactor` 的 `MainLoop` 是核心事件循环，SQ 和 CQ 通过共享内存环形缓冲区和内核交互。利用 Buffer Ring 预注册接收缓冲区，recv 数据零拷贝。
>
> **一致性层**——自研了完整的 Raft 协议。`RaftNode` 实现 Follower/Candidate/Leader 三态转换，单个 `SetRole()` 统一入口管理 timer 和 heartbeat fiber 生命周期。读写路径做了分离：GET 直接 `Schedule` 到分片线程查 hash 表，不经过 Raft；SET/DEL 走 `SubmitCommand` → `FastCommitPath`（单节点 Append+Commit+Apply 三步）或 `ReplicateLog`（多节点等多数派）。`ElectionTimer` 用随机 150-300ms 的 Fiber `SleepFor` 实现选举超时，`HeartbeatLoop` 是 Leader 上 50ms 间隔的心跳 Fiber。
>
> 测试方面有 32 个测试文件覆盖正常路径和故障路径——选举、日志复制、快照创建/传输/恢复、WAL 恢复、分段日志管理、节点崩溃、网络分区都能验证。

### ③ 五分钟项目介绍

（在三分钟基础上增加技术细节和设计权衡）

**补充技术细节**：

> RESP 协议解析部分有两个解析器：一个完整状态机 `RedisParser`（7 个状态，支持嵌套 Array），一个简化版 `ParseMultiBulk`（直接按 `*N`→循环读 `$len`→读数据）。实际生产用简化版，因为 99% 的 Redis 命令都是这种简单 bulk 格式。半包处理靠在 `Connection` 对象中保留 `multibulk_len_` 和 `bulk_len_` 状态变量，返回 `NEED_MORE` 继续读。
>
> CommandRegistry 用了 `absl::flat_hash_map<string_view, CommandId>` 做命令分发，每个 `CommandId` 携带命令名、标记位（WRITE/READONLY/FAST 等）、参数个数、key 位置等元数据。加新命令只需 `registry_ << CI{...}.HFUNC(Handler)` 一行。
>
> RaftEngine 的 `SubmitCommand` 有三条路径：`CommandEncoder::Encode()` 返回 `nullopt`（读命令/PING）→ 直接 `kv_.Apply()`；单节点 (`PeerCount==0`) → `FastCommitPath`；多节点 → `Append` + `ReplicateLog` → 等多数派。`KvStateMachine` 的 `ApplyLogEntry` 从 "SET key val" 字符串解析出命令类型和参数，通过 `Shard(key)` 计算分片，`Await(sid)` 投递到目标分片。
>
> Snapshot 方面做了增量触发（时间阈值 or 命令数阈值），`SnapshotBarrier` 在 snapshot 期间保护读写一致性。AOF 通过 `PersistenceManager` 追加写命令到 `appendonly.aof`，启动时 `ReplayAof` 回放。还有一套独立的快照格式（二进制 key_len+value_len+expire_at）。

**设计权衡**：

> 不做的事情和做的事情一样重要：① 不做跨分片事务（MGET 跨分片时无法保证原子性），简化设计；② 不做复杂数据类型（只支持 String），因为重点是分布式一致性引擎而不是数据结构；③ RPC 层目前是进程内 `LocalTransport`，网络传输层留了接口但未接入——因为当前重点是验证 Raft 协议本身的正确性，网络层可以后续加。

1. **Sharded Storage**: Key hash → Thread binding, Lock-free per shard
2. **Fiber 协程**: User-space cooperative scheduling, 64KB stack, ~50ns switch

5. **Raft Consensus**: Role transitions, Log replication, Snapshot, Joint Consensus
6. **RESP Protocol**: State machine parser, Zero-copy, Half-packet handling
7. **Read/Write Split**: Reads bypass Raft, Writes go through log replication
8. **FastCommitPath**: Single-node optimization, no network overhead

### ⑤ 每题标准回答（精选）

因篇幅限制，此处列出最关键的几个：

**Q17: Raft 三态转换？**

> `SetRole(new_role)` 是唯一的角色切换入口。Follower 状态下若 `ElectionTimer` 超时（150-300ms 随机），调用 `OnElectionTimeout` → `BecomeCandidate`：term++，投自己一票，向所有 peer 发 `VoteRequest`。收到多数票 → `BecomeLeader`：停掉 `ElectionTimer`，启动 `HeartbeatLoop` fiber 每 50ms 发心跳。Leader/Candidate 收到更高 term 的消息 → `BecomeFollower(term)`：更新 term，清空 voted_for，重置选举定时器。这套机制在 `raft_node.cc:140-166`。

**Q27: Snapshot 的时候能写吗？**

> `SnapshotBarrier` 提供了一个读锁。做 snapshot 时 `barrier_->BeginRead()` 获取读锁，普通写操作也获取读锁，snapshot 写入操作需要写锁。所以做 snapshot 期间读写可以并发，但触发 compaction 时才需要写锁阻塞。实现在 `raft/snapshot_barrier.h`。

**Q30: RESP 解析器状态机？**

> 7 个状态：`INIT_S` → 根据首字符分叉到 `ARRAY_LEN_S`（`*`）、`PARSE_ARG_S`（`$`）、`INLINE_S`（其他）。`ARRAY_LEN_S` 解析 `*N\r\n` 中的 N，然后进入 `PARSE_ARG_S` 循环解析每个 arg。`PARSE_ARG_S` 读到 `$N\r\n` 后进入 `BULK_STR_S` 读 N 字节数据。读完一个 arg 进入 `FINISH_ARG_S` 检查是否还有剩余，有的话回到 `PARSE_ARG_S`，没有则到 `CMD_COMPLETE_S`。解析栈 `parse_stack_` 支持嵌套 Array。零拷贝：`bulk_str = str.subspan(0, bulk_len_)` 直接引用 IoBuf 数据。

**Q33: 为什么不用 Redis 源码？优势？**

> Redis 的核心问题是单线程事件循环，受限于单核。我的项目用多线程 key-hash 分片实现水平扩展。此外集成 Raft 提供分布式一致性，配备了完整的 Raft 测试体系。但不是替代 Redis——我的项目不支持复杂数据类型，不是 Redis Drop-in Replace，重点在分布式存储引擎的技术验证。
