# 持久化机制面试准备（结合本项目源码）

> 项目描述："设计 WAL + AOF + Snapshot 持久化机制，实现日志恢复、快照同步及 Log Compaction，提高系统容灾与恢复能力。"

---

## 1. 整体架构

### 1.1 为什么需要三种持久化机制

本项目的持久化包含 **三个独立层次**，分别解决不同问题：

```
Client
  │
  ▼
Service (main_service.cc)           ← AOF 写入 + Snapshot 触发 + Recovery 协调
  │
  ├── persistence_manager_  → AOF 写入
  ├── LoadSnapshot()        → Snapshot 恢复
  ├── ReplayAof()           → AOF 恢复
  └── snapshot_fiber_       → 定时 Snapshot
  │
  ▼
RaftEngine (raft_engine.cc)
  │
  ▼
RaftNode (raft_node.cc)            ← WAL 复制 + commit + apply
  │
  ├── FileLogStorage        → WAL 写入（二进制格式 + CRC32）
  └── RaftSnapshotManager   → Raft 层 Snapshot（压缩日志）
```

| 层次 | 文件格式 | 所属模块 | 解决的问题 |
|------|---------|---------|-----------|
| **WAL** | 二进制 `segment_N.log` | `server/raft/` | Raft 共识复制、节点间日志同步 |
| **AOF** | RESP 文本 `appendonly.aof` | `server/persistence/` | Redis 兼容持久化、可人工阅读的命令日志 |
| **Snapshot** | 二进制 `snapshot.bin` | `server/raft/` + `server/persistence/` | 快速恢复、日志压缩 |

### 1.2 为什么不能只用一种

| 方案 | 问题 |
|------|------|
| **只用 WAL** | 重启后需重放所有日志（百万条），恢复太慢；Raft 日志是二进制格式，没有 CRC 的部分无法被 redis-check-aof 等工具检查 |
| **只用 AOF** | AOF 是文本格式，没有 CRC，没有 segments，无法支持 Raft 的日志复制和 InstallSnapshot |
| **只用 Snapshot** | 快照是定时触发的，两次快照之间的写入数据在崩溃后会全部丢失。必须配 WAL/AOF 记录增量 |

**三者的关系**：Snapshot 是"全量存档"，WAL 是"共识流水账"，AOF 是"Redis 兼容流水账"。Snapshot + WAL 是最小恢复集合（快照还原全量 + WAL 回放增量），AOF 是额外的一层 Redis 兼容保证。

## 2. WAL（Write Ahead Log）

### 2.0 大白话理解 WAL

**什么是 WAL？**

想象你在记账：
- **没有 WAL**：你直接改账本上的数字。突然断电了——账本改到一半，数据乱了。
- **有 WAL**：你先在一张草稿纸上写"我要把 a 的值改成 1"，写完了打个勾。然后再改账本。断电重启后，拿出草稿纸，找到最后一个打勾的记录，把没改完的补上。

WAL 就是那张"草稿纸"——**先写日志到磁盘，再做操作到内存**。

**为什么"先写日志"？**

```
客户端: SET a 1

错误做法: 先改内存
  hash_map["a"] = "1"   ← 内存中完成了
  → 崩溃！              ← 内存全丢，数据没了

正确做法: 先写 WAL
  写磁盘: "SET a 1"     ← 磁盘持久化，崩溃不怕
  hash_map["a"] = "1"   ← 再改内存
  → 崩溃后: 读磁盘日志 → 重放 "SET a 1" → 恢复
```

**在你的项目中的位置**：

```
客户端 SET a 1
    │
    ▼
RaftEngine::SubmitCommand()
    │
    ▼
RaftNode::FastCommitPath()
    │
    ├─[1] log_storage_->Append(entry)    ← 把 "SET a 1" 写入 WAL
    ├─[2] AdvanceCommitIndex()           ← 标记已提交
    └─[3] ApplyCommittedLogs()           ← 真正执行 SET
            └─ KvStateMachine::ApplyLogEntry → DbSlice["a"]="1"
```

### 2.1 文件格式与分段的为什么

WAL 文件按 **segment（段）** 组织：

```
data/
  segment_00000001.log    ← 存第 1-1000 条日志
  segment_00000002.log    ← 存第 1001-2000 条日志
  segment_00000003.log    ← 存第 2001-... 条日志
```

**为什么要分段？** 单个文件无限增长 → `fsync` 越来越慢（每次写整个文件）。分段后旧段可被 Snapshot 覆盖后直接删除（Log Compaction），当前活跃段很小，`fsync` 始终高效。

WAL 的每条记录由 `RecordHeader`（`wal_writer.h:18-23`） + command 数据组成：

```
[RecordHeader: 24 bytes][command_data: N bytes]
  ├── index:  uint64_t (8B)  ← 日志编号
  ├── term:   uint64_t (8B)  ← Raft 任期
  ├── size:   uint32_t (4B)  ← command_data 长度
  └── crc32:  uint32_t (4B)  ← command_data 的 CRC32C
```

`__attribute__((packed))` 确保 header 恰好 24 字节，无对齐填充。

### 2.2 日志追加流程

`WalWriter::Append()`（`wal_writer.cc:88-99`）：

```
① 构造 RecordHeader，填入 index/term/size/crc32
② 将 header 追加到 buf_
③ 将 command 追加到 buf_
```

注意：此时数据还在内存缓冲区，**未落盘**。

`WalWriter::Flush()`（`wal_writer.cc:101-127`）：

```
① fwrite(buf_)        ← 写入 FILE* 缓冲区
② fflush(file_)        ← 刷到内核缓冲区
③ fdatasync(fileno)    ← 强制刷盘（不刷元数据，只刷数据）
④ buf_.clear()         ← 清空内存缓冲区
```

### 2.3 CRC 校验详解

#### 2.3.1 CRC 是什么

CRC = Cyclic Redundancy Check（循环冗余校验）。通俗理解：给数据算一个"指纹"——一样的数据算出一样的指纹，改了哪怕 1 个 bit → 指纹完全不同。

```
"SET a 1"  → CRC32C → 0xA8B9C3D1
"SET a 2"  → CRC32C → 0x7F2E1A04  ← 只改一个字符，结果完全不同
```

#### 2.3.2 为什么需要 CRC

磁盘不是 100% 可靠的，可能发生的故障：

| 故障类型 | 描述 | 没有 CRC 的后果 |
|---------|------|----------------|
| Bit Rot | 磁盘磁场衰减，某 bit 翻转 | 静默错误，WAL 恢复时读到错值 |
| 部分写入 | 崩溃时一条记录只写了一半 | 读到半截 "SET a"，无法解析 |
| 磁盘坏道 | 物理损坏 | 恢复时读到随机垃圾 |

**例子**：WAL 里存的是 `"SET a 1"`，bit rot 翻转 1 位后磁盘上变成 `"SET a 9"`。没有 CRC → 恢复后默默把 a 的值设成 9 → 数据错误永远无法发现。

#### 2.3.3 实现原理

项目用 CRC32C（Castagnoli 变体），256 项查找表（`crc32.h:15-90`）：

写入时（`wal_writer.cc:95`）：**算指纹，存入 header**
```cpp
header.crc32 = ComputeCrc32(entry.command.data(), entry.command.size());
```

恢复时（`segment_log_storage.cc:150-154`）：**重新算，和 header 里的比对**
```cpp
uint32_t computed = ComputeCrc32(entry.command.data(), entry.command.size());
if (computed != hdr.crc32) {
    VLOG(1) << "CRC mismatch - stopping scan";
    break;  // 数据损坏，丢弃本条及之后所有记录
}
```

#### 2.3.4 为什么 CRC 只覆盖 command，不覆盖 header

```
RecordHeader:  [index(8B)][term(8B)][size(4B)][crc32(4B)]
                   ↑            ↑         ↑
              不校验header   不校验     不校验    ← 只校验这部分
                                                    ↓
command_data:   "SET a 1"  ← 只有 command 参与 CRC 计算
```

**设计理由**：
- header 中的 index/term/size 有**冗余检测手段**：部分写入 → 读不够 24 字节 header → 停止；index 不连续 → `hdr.index <= last_index_` → 停止
- command 数据**没有任何冗余信息**，必须靠 CRC 保护

### 2.4 fsync 策略

Flush 的三层缓冲：

```
用户程序 (buf_ 内存)
    │  fwrite()         ← memcpy 到 C 库缓冲区（微秒级）
    ▼
C 标准库缓冲区 (FILE* 内部)
    │  fflush()         ← write() 系统调用到内核（可能不立即写盘）
    ▼
OS 内核缓冲区 (page cache)
    │  fdatasync()      ← 强制内核把数据写入磁盘硬件（毫秒级）
    ▼
磁盘硬件 (物理扇区)      ← 只有这步完成，断电才不丢数据
```

源码（`wal_writer.cc:101-127`）：
```cpp
fwrite(buf_.data(), 1, buf_.size(), file_);   // 第1层: C库缓冲
fflush(file_);                                  // 第2层: 刷到内核
fdatasync(fileno(file_));                       // 第3层: 强制刷盘
```

- WAL：`fwrite` → `fflush` → **`fdatasync`**（落数据，不落元数据如 mtime）
- meta.json（term/voted_for）：写 `.tmp` → `fdatasync` → `rename`（原子替换）
- apply.meta（last_applied）：同上

`fdatasync` vs `fsync`：`fdatasync` 只保证文件数据落盘，不保证元数据（如修改时间、文件大小），比 `fsync` 少一次磁盘写入。对于只追加不修改的 WAL，`fdatasync` 足够。

### 2.5 为什么必须先写 WAL 再 Apply

这是故障恢复的基石。考虑以下场景：

```
时刻 T1: Apply 了一条 SET a=1 到 StateMachine
时刻 T2: 崩溃（WAL 还没写）

崩溃恢复后：StateMachine 里 a=1，但 WAL 里没这条记录。
问题：向其他节点同步时会少一条日志，集群状态不一致。
```

正确的顺序（WAL-first）：

```
T1: 先写 WAL（fsync 落盘）
T2: 再 Apply 到 StateMachine
T3: 崩溃

恢复后：WAL 里有这条记录，ReplayUnappliedLogs 重新 apply → StateMachine 恢复一致。
```

**WAL 是 source of truth，StateMachine 是 derived state**

### 2.6 WAL 恢复流程

`SegmentLogStorage::Open()`（`segment_log_storage.cc:33-48`）：

```
① manifest_.Load()                  ← 读取当前 segment ID
② DiscoverSegments()                ← opendir 扫描目录
    匹配 segment_XXXXXXXX.log 模式，按 ID 排序
③ 对每个 segment 调 ScanSegment()：
    while (true):
        读 RecordHeader (24B)
        → partial header: 停止（写入中断的尾部）
        → index 非严格递增: 停止（异常数据）
        → size == 0: 停止
        读 command_data (hdr.size 字节)
        → partial payload: 停止
        → CRC 不匹配: 停止（数据损坏）
        通过验证 → entries_.push_back + RebuildIndex
④ 更新 base_index_（处理压缩偏移）
```

**Key insight**: 遇到任何异常（部分写、CRC 失败、非单调 index）都"停止扫描当前 segment 及之后"，而不是跳过坏记录继续。这保证了恢复数据的一致性和连续性——Raft 日志的 Log Matching 要求日志是连续无空洞的。

### 2.7 WAL 完整流程图

```
写入:
  RaftNode::ReplicateLog()
      │
      ▼
  FileLogStorage::Append(LogEntry)
      │
      ├── entry.index = last_index_ + 1
      ├── 超过 64MB? → RollSegment() (fclose当前, 新建segment_N.log, manifest++)
      ├── 记录 file_offset = writer_.next_write_offset()
      ├── writer_.Append(entry)
      │     └── RecordHeader + command → buf_ (内存)
      ├── index_.Add(index, segment_id, offset)
      └── [不自动 Flush，由调用者控制]

恢复:
  SegmentLogStorage::Open()
      ├── manifest_.Load()
      ├── DiscoverSegments() → [seg_0, seg_1, ...]
      └── 逐个 ScanSegment():
            ┌─────────────────────────────────┐
            │ fopen("rb")                     │
            │ while(true):                    │
            │   read header(24B)              │
            │   → partial? stop               │
            │   → non-monotonic index? stop   │
            │   → size==0? stop              │
            │   read command(size 字节)        │
            │   → partial? stop               │
            │   → CRC mismatch? stop          │
            │   entries_.push_back(entry)     │
            │   RebuildIndex()                │
            │ fclose()                        │
            └─────────────────────────────────┘
```

**回答模板**：
> "WAL 采用二进制分段格式：每条记录 24 字节 RecordHeader(index/term/size/crc32) + command 数据。写入先到内存 buf，Flush 时 fwrite+fflush+fdatasync 三步落盘。CRC32C 只覆盖 payload，header 损坏靠完整性和单调性检查检测。恢复按 segment 顺序扫描，遇 CRC 失败或非单调 index 停止——保证恢复数据连续无空洞。WAL 先于 Apply 写入，崩溃后 ReplayUnappliedLogs 从 last_applied+1 重放至 LastIndex，保证 StateMachine 与日志一致。"

**追问**：为什么 CRC 只覆盖 payload？（header 损坏通过长度检查和单调 index 也能检测）；为什么不跳过损坏记录？（Raft 日志必须连续，跳过的空洞会导致 index 不连续，破坏 Log Matching）；segment 为什么要分段？（单文件无限增长 → fsync 越来越慢；分段后旧段可删除，压缩效率高）

## 3. AOF（Append Only File）

### 3.1 AOF 为什么存在

AOF 和 WAL 是**两个完全独立的持久化层**，服务于不同目的：

| | WAL (`segment_N.log`) | AOF (`appendonly.aof`) |
|---|---|---|
| **格式** | 二进制 `RecordHeader + command` | RESP 文本 `*3\r\n$3\r\nSET\r\n...` |
| **用途** | Raft 节点间日志复制 | Redis 兼容持久化 |
| **CRC** | CRC32C | **无** |
| **落盘** | `fdatasync` | `fflush`（**无 fsync！**） |
| **分段** | 64MB 自动分段 | 单文件 |
| **恢复** | `SegmentLogStorage::Open()` 扫描 | `ReplayAof()` 解析 RESP |

### 3.2 命令如何写入 AOF

`PersistenceManager::RecordCommand()`（`persistence_manager.cc:20-24`）：

```cpp
void RecordCommand(const vector<string>& args) {
    string resp = CommandSerializer::Serialize(args);  // ① 转为 RESP 文本
    aof_writer_.Append(resp);                          // ② 追加到内存 buf
    aof_writer_.Flush();                               // ③ fwrite + fflush
}
```

`CommandSerializer::Serialize()` 做的事：
```
输入: ["SET", "a", "1"]
输出: "*3\r\n$3\r\nSET\r\n$1\r\na\r\n$1\r\n1\r\n"
```

调用点在 `Service::Set()` / `Del()` / `Expire()` 中（`main_service.cc:329,386`），在 Raft 提交完成后：

```cpp
engine_.SubmitCommand(cid, args);              // 先走 Raft
persistence_manager_->RecordCommand(cmd_args);  // 再写 AOF
```

### 3.3 AOF 写入时机问题

**现状**：AOF 的 `Flush()` 只做 `fflush`（`aof_writer.cc:49`），**不做 `fdatasync`**。这意味着命令写入后可能仍在操作系统缓冲区中，进程崩溃（非 OS 崩溃）不会丢失，但 **Kill -9 或断电可能丢失最后一条 AOF 记录**。

相比之下，WAL 的 `Flush()` 做了 `fdatasync`（`wal_writer.cc:120`），保证落盘。

### 3.4 AOF Rewrite

**未实现**。当前是单文件无限追加，没有压缩/重写机制。随着运行时间增长，AOF 文件会无限变大，恢复时需重放所有命令。

### 3.5 为什么我的项目设计 AOF

即使已有 WAL（Raft 共识需要的日志），AOF 仍有存在价值：

1. **Redis 兼容性**：redis-check-aof 可以检查 AOF 文件内容，redis-cli 可以直接 `--pipe` 导入 AOF。WAL 的二进制格式无法被 Redis 工具处理。
2. **可人工阅读**：AOF 是 RESP 文本，运维可以直接 `cat appendonly.aof` 看到最近执行了哪些命令。WAL 是二进制不可读。
3. **独立恢复路径**：即使 Raft 元数据损坏，AOF 仍可独立恢复数据（`ReplayAof` 走 `DispatchCommand` 正常执行）。

**但有两个已知问题**：
- `Load()` 硬编码了文件名 `"appendonly.aof"`，忽略了 `Open()` 传入的路径（`persistence_manager.cc:31`）
- AOF `Flush` 没有 `fdatasync`，Kill -9 可能丢最后一条记录

## 4. Snapshot

### 4.1 为什么需要 Snapshot

日志无限增长 → 三个问题：

| 问题 | 无 Snapshot 的后果 | Snapshot 如何解决 |
|------|------------------|------------------|
| **磁盘占用** | WAL 文件无限积累 | 快照后删除旧 WAL segments |
| **恢复速度** | 需重放所有日志（百万条） | 加载快照（全量）+ 重放增量（少数） |
| **新节点同步** | 必须发全部日志 | 发快照（一次传输） |

### 4.2 两层 Snapshot 架构

项目有两套 Snapshot 体系：

| | Raft 层 (`RaftSnapshotManager`) | Server 层 (`SnapshotManager` + `SnapshotFiber`) |
|---|---|---|
| **文件** | `raft/group_0/snapshot/snapshot.bin` | `snapshot.bin` |
| **触发** | 日志超 `log_gap_` (100K) 条 | 定时（`--snapshot_time_sec`）或命令数（`--snapshot_cmd_count`） |
| **内容** | `KvStateMachine::SaveSnapshot` | `Service::CreateSnapshot` → `StateSerializer::Export` |
| **压缩** | 调 `CompactLogs` 删 WAL | 不压缩日志 |
| **传输** | InstallSnapshot RPC | 不传输（本地快照） |

### 4.3 Snapshot 文件内容

`SnapshotWriter` 写的格式（`snapshot_writer.cc`）：

```
[header:  4B magic "SNAP" (0x50414E53) + 4B num_records]
[record1: 4B key_len + 4B value_len + 8B expire_at + key_bytes + value_bytes]
[record2: ...]
```

### 4.4 Snapshot 生成流程

`RaftSnapshotManager::CreateSnapshot()`（`snapshot_manager.cc:41-74`）：

```
① barrier_.BeginWrite()        ← 暂停所有写入
② state_machine_->SaveSnapshot("snapshot.bin")
     └── StateSerializer::Export() 将所有 shard 的 KV 导出
     └── SnapshotWriter::Finalize() fflush+fdatasync+rename
③ meta_storage_.SetMeta({last_index, last_term, timestamp})
     └── 写 snapshot.meta (JSON, 原子 rename)
④ log_storage_->CompactLogs(last_index, last_term)
     └── SetSnapshotAnchor(index, term)
     └── CompactSegments(snapshot_index)  ← 删除旧 WAL segment 文件
     └── CompactUpTo(snapshot_index)      ← 清理内存 entries
⑤ barrier_.EndWrite()          ← 恢复写入
```

**为什么 Snapshot 不会破坏一致性**：`SnapshotBarrier` 是 readers-writer 锁。`BeginWrite` 设 `writing_=true`，阻塞所有新写；等待 `readers_` 降到 0，所有正在执行的写操作完成。此时状态机处于"静止"状态，导出的是**逻辑时间点一致的快照**。

### 4.5 InstallSnapshot RPC（`snapshot_sender.h`）

Leader 发 `AppendEntries` 前先判断（`raft_node.h:247`）：

```cpp
bool ShouldInstallSnapshot(next_index, snapshot_index) {
    return snapshot_index > 0 && next_index <= snapshot_index;
}
// Follower 需要的下一条日志已被压缩 → 发快照
```

Sender（Leader 侧）：读 `snapshot.bin`，按 64KB 分块，逐块发 `InstallSnapshotRequest(offset, data, done)`。

Receiver（Follower 侧）：`OnInstallSnapshot`（`raft_node.cc:661-715`）→ `HandleChunk` 写 `.recv.tmp` → 末块 `fflush + fdatasync + rename → snapshot.bin` → `LoadSnapshot` → `log_storage_->Clear()` → 更新 `last_applied/commit_index`。

### 4.6 Snapshot 恢复流程

`Service::Init()`（`main_service.cc:66-113`）：

```
① Service::LoadSnapshot()       ← 服务器级快照恢复
     └── SnapshotManager::Load("snapshot.bin")
     └── StateSerializer::Import → 导入各 shard 的 DbSlice

② RaftNode::SetStoragePath()    ← Raft 层恢复
     └── apply_progress_.Load()        ← 读 apply.meta
     └── SnapshotLoader::Load()        ← 验证 snapshot.meta + snapshot.bin
     └── state_machine_->LoadSnapshot()
     └── SetSnapshotAnchor(index, term)
```

实际上，服务器级的 `LoadSnapshot()` 和 Raft 层的 `SetStoragePath` 加载的是**同一份数据**——服务器级走 `Service::LoadSnapshot` 恢复 KV，Raft 层走 `KvStateMachine::LoadSnapshot` 恢复。两者路径不同但目标一致。

## 5. Log Compaction（日志压缩）

### 5.1 为什么需要 Log Compaction？

在 Raft 中，leader 每收到一个客户端请求就追加一条日志条目。随着时间推移，日志无限增长。但一旦某条日志被 **应用到状态机**（apply），它的效果已经体现在状态机的状态中，日志本身对于 **故障恢复** 来说就是冗余的了。

问题：
- **内存占用无限增长**：`entries_` 向量中累积百万条日志条目
- **重启 replay 越来越慢**：每次启动需重放所有历史日志
- **InstallSnapshot RPC 传输量大**：新节点加入需同步全部日志

**解决方案**：定期对状态机做快照（snapshot），然后丢弃快照覆盖的旧日志，同时保留足够元数据来满足 Raft 的 AppendEntries 一致性检查。

### 5.2 Compaction 做什么

Snapshot 创建后，快照覆盖范围内的 WAL 条目可以删除。项目分三步执行（`segment_log_storage.cc:288-293`）：

```cpp
void SegmentLogStorage::CompactLogs(LogIndex snapshot_index, Term snapshot_term) {
  SetSnapshotAnchor(snapshot_index, snapshot_term);
  CompactSegments(snapshot_index);
  CompactUpTo(snapshot_index);
}
```

### 5.3 完整流水线

```
SnapshotLoop (后台 fiber, 每秒检查)
    │
    ▼
ScheduleCreateIfNeeded()
    │ 检查 last_index - snapshot_index >= log_gap_ (默认 100K)
    ▼
CreateSnapshot()
    │ 1. barrier_.BeginWrite()  — 暂停所有写入
    │ 2. state_machine_->SaveSnapshot("snapshot.bin") — 导出全量 KV
    │ 3. meta_storage_.SetMeta({last_index, last_term}) — 记录元数据
    │ 4. log_storage_->CompactLogs(last_index, last_term) — ★ 核心
    │ 5. barrier_.EndWrite()    — 恢复写入
    ▼
CompactLogs()
    ├── SetSnapshotAnchor(index, term)   — 保存锚点
    ├── CompactSegments(index)           — 删除磁盘上的旧 WAL 段
    └── CompactUpTo(index)               — 清理内存中的旧日志
```

### 5.4 三阶段压缩详解

#### 阶段一：SetSnapshotAnchor — 保存"锚点"

```cpp
// segment_log_storage.cc:198
void SegmentLogStorage::SetSnapshotAnchor(LogIndex index, Term term) {
  anchor_.index = index;
  anchor_.term = term;
}
```

**作用**：保存快照最后一个日志条目的 `(index, term)` 到 `SnapshotAnchor` 结构体（`raft_types.h:108-114`）。

**为什么需要 Anchor？** 假设快照覆盖到 index 10000。压缩后 index ≤ 10000 的日志条目被删除。但 Raft 的 AppendEntries RPC 需要检查 `prevLogIndex` 和 `prevLogTerm`：如果 follower 的 `last_index` 刚好是 10000，leader 发来的 `prevLogIndex = 10000`，follower 必须能返回 `prevLogTerm`。

Anchor 机制在 `ILogStorage::GetTerm()` 中优先处理（`log_storage.h:39-43`）：

```cpp
virtual Term GetTerm(LogIndex index) const {
  if (index == anchor_.index && anchor_.index > 0)  // ← 优先检查 anchor
    return anchor_.term;
  const LogEntry* e = Get(index);
  return e ? e->term : 0;  // 不在 anchor 且不在内存中 → 返回 0
}
```

- `GetTerm(10000)` → 返回 anchor 中保存的 term（正确）
- `GetTerm(9999)` → 返回 0（无可奉告，因为这个数据在 leader 那边也应该被压缩了）
- `GetTerm(10001)` → 从 `entries_` 中查找（如果还在内存中的话）

这样，leader 发送 AppendEntries 携带 `prevLogIndex=10000, prevLogTerm=X` 时，follower 用 `GetTerm(10000)` 返回正确的 term → `prevLogTerm` 匹配 → 检查通过。

#### 阶段二：CompactSegments — 删除磁盘上的 WAL 段文件

```cpp
// segment_log_storage.cc:303
void SegmentLogStorage::CompactSegments(LogIndex snapshot_index) {
  if (dir_.empty())
    return;

  // 通过 WalIndex 找到 snapshot_index 所在的 segment ID
  const EntryLocation* loc = index_.Find(snapshot_index);
  if (!loc) {
    // WalIndex 可能已被 Clear，保守跳过
    return;
  }

  uint32_t keep_segment = loc->segment_id;

  // 扫描目录，删除 ID < keep_segment 的所有段文件
  auto segments = DiscoverSegments();
  for (uint32_t seg_id : segments) {
    if (seg_id >= keep_segment)
      break;
    std::string seg_path = SegmentPath(seg_id);
    if (unlink(seg_path.c_str()) == 0) {
      VLOG(1) << "Deleted WAL segment: " << seg_path;
    }
  }
}
```

**作用**：删除磁盘上 **完全被快照覆盖** 的 WAL 段文件。

关键设计：
- 通过 `WalIndex` 找到 `snapshot_index` 所在的段 ID（`keep_segment`）
- 只删除 `seg_id < keep_segment` 的段（这些段里的所有条目 index ≤ snapshot_index）
- 包含 `snapshot_index` 的段 **保留**（`seg_id == keep_segment`），因为：
  1. 启动恢复时需要从该段重建 WalIndex
  2. `GetRange()` 可能需要读取该段中的少量条目
- `unlink()` 是 POSIX 系统调用，立即删除文件，释放磁盘空间

**为什么保留 `keep_segment`？** 测试 `KeepSnapshotSegment` 验证了这一点：压缩后 `GetTerm(snapshot_index)` 应该返回正确的 term（通过 anchor），而段文件保留为下次重启后 rebuild WalIndex 用。

#### 阶段三：CompactUpTo — 清理内存中的旧日志

```cpp
// segment_log_storage.cc:258
bool SegmentLogStorage::CompactUpTo(LogIndex index) {
  if (index <= base_index_)
    return true;  // 已经压缩过了

  if (index >= last_index_) {
    // 全部压缩，只保留 sentinel
    base_index_ = index;
    index_.Clear();
    last_index_ = index;
    last_term_ = 0;
    entries_.resize(1);  // 只保留 index 0 的 sentinel
    return true;
  }

  // 部分压缩：将未压缩的条目前移，覆盖已删除的区域
  size_t keep_from = index - base_index_ + 1;
  if (keep_from < entries_.size()) {
    std::move(entries_.begin() + keep_from, entries_.end(),
              entries_.begin() + 1);
    entries_.resize(entries_.size() - keep_from + 1);
  } else {
    entries_.resize(1);
  }
  base_index_ = index;
  index_.Clear();  // WalIndex 失效 — 懒重建
  return true;
}
```

**作用**：从内存 `entries_` 向量中移除 index ≤ `snapshot_index` 的条目，更新 `base_index_`。

关键细节：
- **`base_index_`**：更新为 `snapshot_index`，表示 log 的"逻辑起点"。之后 `FirstIndex()` 返回 `base_index_ + 1`。
- **`index_.Clear()`**：清空 WalIndex。因为 `CompactUpTo` 做了 `std::move` 将后部的条目前移，所有 entry 在 vector 中的物理位置发生了变化，旧的 WalIndex 映射（`log_index → (segment_id, offset)`）全部失效。简单清空，后续访问时通过 `DiscoverSegments()` 懒重建。
- **`entries_.resize(1)`**：只保留 index 0 的 sentinel entry。sentinel 始终存在，这是所有 ILogStorage 实现的约定（简化 off-by-one 处理）。
- **内存回收**：`std::move` 将后续条目向前搬移，`resize` 缩小 vector，已删除条目的内存被释放。

### 5.5 三种 ILogStorage 实现的差异

| 实现 | 用途 | CompactUpTo | CompactSegments | 磁盘清理 |
|------|------|-------------|-----------------|---------|
| **CommandLog** | 纯内存测试 | 只动 `entries_` vector + `base_index_` | 无 | 无 |
| **FileLogStorage** | 单文件 WAL | 更新 `base_index_` + 清 `index_` + `log_size_` | 无（单个文件不切段） | 无 |
| **SegmentLogStorage** | 生产级分段 WAL | 同 CommandLog，额外清 `index_` | `unlink()` 删除旧段文件 | ✅ |

**FileLogStorage::CompactUpTo**（`file_log_storage.cc:243-263`）：

```cpp
bool FileLogStorage::CompactUpTo(LogIndex index) {
  if (index <= base_index_)
    return true;
  if (index >= last_index_) {
    base_index_ = index;
    log_size_ = 0;
    last_index_ = index;
    last_term_ = 0;
    index_.Clear();
    return true;
  }
  base_index_ = index;
  log_size_ = last_index_ - index;
  index_.Clear();
  return true;
}
```

FileLogStorage 是单文件 WAL，没有分段，所以压缩只更新元信息（`base_index_`、`log_size_`），不删除磁盘文件。磁盘上被压缩的旧条目只是变得"不可达"——`Get()` 通过 WalIndex 查找，WalIndex 被清空后旧条目无法被访问，但它们仍然占据磁盘空间，直到文件被轮转覆盖。

**CommandLog::CompactUpTo**（`command_log.cc:92-115`）：

纯内存实现，用于测试。只从 `entries_` vector 中移除条目，没有 WalIndex 和磁盘操作。

### 5.6 SnapshotBarrier — 一致性保证

```cpp
// snapshot_manager.cc:41-74
bool RaftSnapshotManager::CreateSnapshot() {
  barrier_.BeginWrite();     // 暂停所有状态机写入
  bool ok = state_machine_->SaveSnapshot("snapshot.bin");  // 导出"冻结"的快照
  if (ok) {
    log_storage_->CompactLogs(last_index, last_term);  // 压缩日志
  }
  barrier_.EndWrite();       // 恢复写入
  return ok;
}
```

**SnapshotBarrier** 是一个 readers-writer 锁（`snapshot_barrier.h`）：
- `BeginWrite()` — 设置 `writing_=true`，阻塞 **所有新的写入操作**；等待当前正在执行的写入操作完成（`readers_` 降为 0）
- 快照保存期间，Raft 日志继续接收新条目追加到 WAL，但 **状态机停止 apply 新日志**
- `EndWrite()` — `writing_=false`，恢复状态机写入

这样保证了 `snapshot.bin` 文件是状态机在某个逻辑时间点的 **一致视图**。

### 5.7 触发条件

```cpp
// snapshot_manager.cc:76
bool RaftSnapshotManager::ScheduleCreateIfNeeded() {
  LogIndex last_index = log_storage_->LastIndex();
  LogIndex snapshot_index = meta_storage_.meta().index;
  if (last_index < snapshot_index + log_gap_)

`log_gap_` 默认值：**100,000**（在 `snapshot_manager.h` 中定义）。

触发时序：
- 第一次快照在 index 达到 100K 时触发
- 之后每 100K 日志条目创建一个新快照
- 每次快照后自动触发日志压缩

void RaftSnapshotManager::SnapshotLoop() {

    ScheduleCreateIfNeeded();
    // 每秒检查，避免忙轮询
    for (int i = 0; i < 1000 && !shutdown_.load(std::memory_order_acquire); i++) {
      util::ThisFiber::SleepFor(std::chrono::milliseconds(1));
    }
  }
}
```

### 5.8 崩溃恢复中的 Log Compaction 处理

启动时 `RaftNode::SetStoragePath()` 处理恢复（`raft_node.cc:36-74`）：

```cpp
void RaftNode::SetStoragePath(std::string_view path) {
  // 1. 尝试加载现有快照
  SnapshotLoadStatus status = SnapshotLoader::Load(snapshot_dir_);
  if (status == SnapshotLoadStatus::Ok) {
    state_machine_->LoadSnapshot(snapshot_dir_ + "snapshot.bin");
    // 2. 从 snapshot.meta 获取 last_index / last_term
    LogIndex snap_index = meta_storage_.meta().index;
    Term snap_term = meta_storage_.meta().term;
    // 3. 设置 anchor，使 GetTerm(snap_index) 在压缩后仍有效
    log_storage_->SetSnapshotAnchor(snap_index, snap_term);
  }
  // 4. 扫描 WAL segments 加载 index > snap_index 的增量日志
  log_storage_->Open(wal_dir_);
}
```

恢复流程：
1. 加载 `snapshot.bin` 到状态机 → 状态恢复到快照时刻
2. 从 `snapshot.meta` 读取 `(index, term)` → 调用 `SetSnapshotAnchor()`
3. 扫描 WAL segments，只加载 **index > snapshot_index** 的增量日志
4. `ReplayUnappliedLogs` 从 `last_applied+1` 重放到 `LastIndex`

这样重启只需回放快照之后（~100K）的日志，而不是从头 replay 全部历史。

### 5.9 为什么安全

**安全性保证**：

| 保证 | 机制 |
|------|------|
| **数据不丢失** | Snapshot 文件已 fsync 落盘 + `snapshot.meta` 原子写 → Compact 后崩溃，可从 snapshot 恢复 |
| **一致性检查不失效** | `SetSnapshotAnchor` 保留 `(index, term)` → `GetTerm(snapshot_index)` 返回正确的 term |
| **增量日志保留** | 只删除 index ≤ `snapshot_index` 的条目，index > `snapshot_index` 的日志完整保留 |
| **未提交日志不会被压缩** | Compaction 在 snapshot 创建后触发，snapshot 只包含已提交的条目 |
| **磁盘安全** | 包含 `snapshot_index` 的段文件被保留，不会误删 |
| **Raft Log Matching** | `anchor_.index` 作为"逻辑日志起点"，leader 的 `prevLogIndex` 不应小于此值，否则 leader 应发 InstallSnapshot |

### 5.11 面试点

**Q：Log Compaction 为什么安全？**
> Compaction 发生在 Snapshot 创建并落盘之后：snapshot.bin + snapshot.meta 已 fsync → 数据不会丢；只删除快照中已包含的 index 之前的 WAL → 快照未覆盖的日志保留；SnapshotAnchor 保留关键 (index, term) → 一致性检查不失效。

**Q：SnapshotAnchor 是什么？为什么压缩后需要它？**
> SnapshotAnchor 是结构体 `{index, term}`，保存在每个 ILogStorage 实例中。压缩后 `GetTerm(snapshot_index)` 仍能通过 anchor 返回正确的 term，使 AppendEntries RPC 的 `prevLogTerm` 一致性检查继续有效。否则 `GetTerm(snapshot_index)` 会返回 0，导致 leader 认为 follower 日志不一致而触发回滚。

**Q：CompactSegments 和 CompactUpTo 的区别？**
> CompactSegments 删除磁盘上的 WAL 段文件（`unlink`），释放磁盘空间。CompactUpTo 清理内存 `entries_` 向量，释放内存。两者相辅相成：磁盘旧段删除后不可能再被读取；内存旧条目删除后 WalIndex 被清空，后续访问通过 `DiscoverSegments()` 懒重建。

**Q：为什么快照所在的 segment 被保留？**
> 保留包含 `snapshot_index` 的 segment 是为了满足两个场景：① 节点重启时 `Open()` 读取该 segment 重建 WalIndex；② 如果恢复时 WAL 中有紧邻 `snapshot_index` 之后的条目，需要从该 segment 的尾部开始读取。该 segment 中被 `snapshot_index` 覆盖的条目虽然仍在磁盘上，但通过 WalIndex 不可达（WalIndex 在 CompactUpTo 被 Clear）。

## 6. Recovery（崩溃恢复）

### 6.1 完整恢复流程

```
节点启动 (Service::Init)
│
├── ① shard_set_.Init()                   ← 初始化分片存储
│
├── ② LoadSnapshot()                      ← 加载服务器级快照
│     └── snapshot.bin → StateSerializer::Import → DbSlice
│
├── ③ RaftGroup::InitStorage()            ← Raft 层恢复
│     └── RaftNode::SetStoragePath()
│           ├── apply.meta → last_applied_
│           ├── snapshot.meta + snapshot.bin → LoadSnapshot
│           │     └── last_applied_ = max(last_applied_, snapshot.index)
│           │     └── SetSnapshotAnchor
│           └── meta.json → current_term, voted_for
│
├── ④ SegmentLogStorage::Open()           ← 扫描 WAL segments
│     └── DiscoverSegments → ScanSegment × N
│           └── CRC 校验 → entries_ 加载到内存
│
├── ⑤ BootstrapSingleNode()              ← 单节点直接变 Leader
│
├── ⑥ ReplayAof()                         ← AOF 命令重放
│     └── 读取 appendonly.aof → ParseResp → DispatchCommand
│
└── ⑦ 开始提供服务
```

### 6.2 为什么恢复顺序这样设计

1. **先 ShardInit**：存储层必须先就绪，否则 LoadSnapshot 无处导入
2. **再 LoadSnapshot**：恢复全量数据（最快的恢复路径）
3. **再 Raft 恢复**：恢复 term/vote_for → 确定"我是谁"；恢复 last_applied → 知道 apply 到了哪里（详见 6.2.1）
4. **再 WAL 扫描**：加载增量日志到内存，为 ReplayUnappliedLogs 做准备
5. **ReplayUnappliedLogs**：从 last_applied+1 到 LastIndex 重放 WAL 增量
6. **最后 AOF**：额外的 Redis 兼容恢复层（注意：AOF 和 WAL 有重叠，AOF 恢复可能重复执行已 apply 的命令，但因为 replay_mode_ 是幂等的所以无影响）

#### 6.2.1 Raft 恢复详解：term/voted_for 和 last_applied

这一步由 `RaftNode::SetStoragePath()` 执行（`raft_node.cc:36-74`），从磁盘加载两个关键元数据文件：

```
RaftNode::SetStoragePath("data/raft")
  │
  ├── meta.json       →  current_term, voted_for    ← "我是谁"
  └── apply.meta      →  last_applied               ← "apply 到了哪里"
```

---

##### ① meta.json：current_term + voted_for — "确定我是谁"

**文件路径**：`data/raft/meta.json`  
**处理代码**（`raft_node.cc:43-44`）：

```cpp
storage_ = RaftStorage(path + "meta.json");
storage_.Load();
```

**磁盘上的内容**：

```json
{"current_term":3,"voted_for":"node-2"}
```

**`RaftStorage` 类**（`raft_storage.h`）维护两个关键状态：

| 字段 | 类型 | 含义 |
|------|------|------|
| `current_term_` | `Term`（uint64_t） | 节点当前所处的 Raft 任期 |
| `voted_for_` | `NodeId`（string） | 在当前任期中已投票给了哪个节点（空串表示未投票） |

**为什么需要恢复这两个字段？**

Raft 的安全性（Election Safety）保证：**每个任期最多只有一个 leader**。这一保证依赖以下规则：

- 节点只能给**每个任期投一票**（`voted_for`）
- 节点只投票给**任期不低于自己**的 candidate（`current_term`）
- candidate 当选后，所有 follower 在该任期不会再投票给别人

如果不恢复 `current_term` 和 `voted_for`，重启后的节点会从 term 0 开始，可能：
1. 以更低的任期号发起选举 → 干扰现有集群
2. 给两个不同 candidate 投票（在同一任期）→ 违反 Election Safety
3. 当选后因 term 太低被其他节点拒绝

**原子写保证**（`raft_storage.cc:103-126`）：

```cpp
// RaftStorage::Flush()
std::string tmp_path = path_ + ".tmp";
std::string content = Serialize();
WriteAndFsync(tmp_path, content);     // ① 写 .tmp 文件 + fdatasync
AtomicRename(tmp_path, path_);         // ② 原子 rename 覆盖原文件
```

两步保证：
- **写入中断**：.tmp 文件可能不完整，但原 meta.json 完好无损（未被覆盖）
- **rename 是原子的**（POSIX 保证）：要么全部完成，要么原文件不变
- 因此 term/voted_for 的写入是 **all-or-nothing** 的

**更新时机**（谁在写 meta.json）：

| 场景 | 调用方 | 更新内容 |
|------|--------|---------|
| 发现更高 term | `RaftNode::SetTerm()` | `current_term` + 清空 `voted_for` |
| 投票给 candidate | `RaftNode::RequestVote()` | `voted_for = candidate_id` |
| 新 leader 当选 | `RaftNode::BecomeLeader()` | `voted_for = self` |

每次更新都立即 `Flush()` → `fdatasync` 落盘。

##### ② apply.meta：last_applied — "知道 apply 到了哪里"

**文件路径**：`data/raft/apply.meta`  
**处理代码**（`raft_node.cc:46-48`）：

```cpp
apply_progress_ = ApplyProgress(path + "apply.meta");
apply_progress_.Load();
last_applied_ = apply_progress_.LastApplied();
```

**磁盘上的内容**：

```json
{"last_applied":10042}
```

**`ApplyProgress` 类**（`apply_progress.h`）维护一个字段：

| 字段 | 类型 | 含义 |
|------|------|------|
| `last_applied_` | `LogIndex`（uint64_t） | 已应用到状态机的最后一条日志的 index |

**为什么需要恢复 last_applied？**

节点崩溃前可能已经 apply 了一部分日志到状态机，但没来得及 apply 所有已提交的日志。重启后需要：
1. 知道从哪里**继续 apply**（`last_applied_ + 1`）
2. 避免**重复 apply** 已经执行过的操作

没有 `last_applied` 的后果：
- 从 index 1 开始全部重放 → 重复执行所有 SET/DEL → 如果操作不是幂等的就会出错
- 不知道已经 apply 到哪里了 → 和 leader 同步时无法确定 `next_index`

**apply.meta 的更新时机**（`raft_node.cc` 中 `ApplyCommittedLogs` 的调用链）：

```
ApplyCommittedLogs()
  for (index = last_applied_ + 1; index <= commit_index_; index++)
    state_machine_->ApplyLogEntry(entries_[i])   // 执行 SET / DEL
    apply_progress_.Update(index)                 // 每 apply 一条就 fdatasync
```

**每 apply 一条就 fsync 一次** —— 这看起来性能很差，但保证了 **at-most-once 语义**：
- 崩溃前 apply 了 10 条，apply.meta 记录了 index 10
- 崩溃后重启，从 index 11 开始重放
- 不会重复执行 index 1~10 的操作

**与 Snapshot 的交互**（`raft_node.cc:58-62`）：

```cpp
// 如果存在 snapshot，取 max(last_applied, snapshot_index)
if (state_machine_->LoadSnapshot(loaded.bin_path)) {
  last_applied_ = std::max(last_applied_, loaded.meta.index);
  // ...
  apply_progress_.Update(last_applied_);
}
```

这是因为：
- 快照加载后，状态机已经回到 `snapshot_index` 时刻的状态
- 但 `apply.meta` 中的 `last_applied` 可能比 `snapshot_index` **更大**（如果崩溃前已经 apply 了快照之后的增量）
- 取 `max` 保证不丢失已经 apply 的进度
- `apply_progress_.Update()` 把更新后的值写回磁盘

##### ③ 两个文件在恢复流程中的位置

```
RaftNode::SetStoragePath()
  │
  ├── 1. storage_.Load()           ← meta.json: 恢复 current_term / voted_for
  │                                  └── 此时节点知道"我在 term 3，投给了 node-2"
  │
  ├── 2. apply_progress_.Load()    ← apply.meta: 恢复 last_applied
  │                                  └── 此时节点知道"我已经 apply 到了 index 10042"
  │
  ├── 3. SnapshotLoader::Load()    ← 检查 snapshot.meta + snapshot.bin
  │    ├── 存在且有效 → LoadSnapshot()
  │    │   ├── last_applied_ = max(last_applied_, snapshot_index)
  │    │   └── SetSnapshotAnchor(snapshot_index, snapshot_term)
  │    └── 不存在或损坏 → 跳过（依赖 WAL 完全恢复）
  │
  ├── 4. log_storage_->Open()      ← WAL 扫描
  │    └── 只加载 index > snapshot_index 的增量日志
  │
  ├── 5. BootstrapSingleNode()     ← 单节点自动成为 Leader
  │
  └── 6. ApplyCommittedLogs()      ← 从 last_applied+1 开始 apply
```

**为什么先恢复 meta.json / apply.meta，再扫描 WAL？** 因为 WAL 扫描需要知道 `base_index_` 来正确加载。`base_index_` 由 `SetSnapshotAnchor` 设置，而 anchor 的值来自 `snapshot.meta`。如果先扫描 WAL 再加载 snapshot，已压缩的 WAL 段中 index 小于 snapshot_index 的条目已经不存在了，扫描无法正确确定日志的起始点。

##### ④ 文件内容一览

| 文件 | 路径 | 格式 | 内容示例 | 原子写 | fsync |
|------|------|------|---------|--------|-------|
| **meta.json** | `data/raft/meta.json` | JSON | `{"current_term":3,"voted_for":"node-2"}` | ✅ .tmp + rename | ✅ fdatasync |
| **apply.meta** | `data/raft/apply.meta` | JSON | `{"last_applied":10042}` | ✅ .tmp + rename | ✅ fdatasync |
| **snapshot.meta** | `data/raft/snapshot/snapshot.meta` | JSON | `{"index":10000,"term":3,"timestamp_ms":...}` | ✅ .tmp + rename | ✅ fdatasync |

三个文件都使用 **write .tmp → fdatasync → rename** 的原子写模式，保证了崩溃安全。

**为什么不用 SQLite / RocksDB？** 每个文件只存 1-2 个简单字段，JSON 文件 + 原子 rename 足够可靠且实现简单。没有事务需求（三个文件独立写入），不需要引入重量级存储引擎。

#### 6.2.2 确定主机（Leader）/ 从机（Follower）

恢复完 term/voted_for 和 last_applied 之后，节点是如何确定自己是主机还是从机的？

**答案：节点启动后统一从 Follower 开始，通过 Raft 选举决定角色。**

具体有三种途径：

##### 途径一：单节点集群 — BootstrapSingleNode（`raft_node.cc:184-200`）

```cpp
bool RaftNode::BootstrapSingleNode() {
  if (role_ == RaftRole::Leader)
    return true;
  if (!GetPeerIds().empty())
    return false;          // 有 peers → 不能跳过选举
  BecomeCandidate();       // term += 1, 投票给自己
  BecomeLeader();          // 1/1 = majority, 直接当选
  return true;
}
```

这是最特殊的情况。如果配置是单节点（没有 peers），重启后直接成为 Leader：
- `GetPeerIds()` 返回空列表（`cluster_config_.voters` 中只有自己）
- `BecomeCandidate()` → term 自增 1，`set_voted_for(self)`，`vote_count_ = 1`
- `BecomeLeader()` → 1 人中 1 人投票，majority = 1，自动当选
- **不需要等待选举超时，不需要网络通信**

**调用时机**（`main_service.cc:98-110`）：

```cpp
// Init() 中：先 LoadSnapshot → Raft 恢复 → 再 Bootstrap
if (engine_.BootstrapSingleNode()) {
  LOG(INFO) << "Raft: node is Leader (single-node bootstrap)";
}
```

**为什么要在 AOF 重放之前执行？** 因为 AOF 重放走 `SubmitCommand`，需要节点是 Leader 才能成功提交。先 bootstrap 成 Leader，AOF 重放的 SET/DEL 才能正常通过 Raft 路径。

##### 途径二：多节点集群 — 竞选流程

这是标准 Raft 选举流程：

**① 启动时默认 Follower**

```cpp
// raft_node.h:337 — 默认值，未显式设置前就是 Follower
RaftRole role_ = RaftRole::Follower;
```

**② 启动选举定时器**

```cpp
// SetRole(Follower) 中触发（raft_node.cc:138-150）
case RaftRole::Follower:
  storage_.set_voted_for("");       // 清空投票记录
  vote_count_ = 0;
  if (!election_started_) {
    election_started_ = true;
    election_timer_.Start([this] { StartElection(); });
  }
  election_timer_.Reset();          // 重置定时器，开始倒计时
  break;
```

**③ 收到 Leader 心跳 → 保持 Follower**

如果集群中已有 Leader，它会定期发送 AppendEntries（心跳）。每次收到，`election_timer_.Reset()` 重置超时。节点只要持续收到心跳，就一直保持 Follower。

**④ 选举超时 → 发起竞选**

如果定时器到期（没有收到任何心跳），节点认为 Leader 已宕机：

```cpp
void RaftNode::OnElectionTimeout() {
  if (role_ != RaftRole::Follower)
    return;    // 已经是 Candidate/Leader 的不再触发
  BecomeCandidate();
}
```

`BecomeCandidate()` 触发 `SetRole(Candidate)`：

```cpp
case RaftRole::Candidate:
  storage_.set_current_term(storage_.current_term() + 1);  // term++
  storage_.set_voted_for(node_id_);                         // 投给自己
  vote_count_ = 1;                                          // 自己的一票
  election_timer_.Deactivate();                              // 停止选举计时
  break;
```

**⑤ 发起投票（`StartElection` — `raft_node.cc:248-293`）**

```cpp
ElectionResult RaftNode::StartElection() {
  BecomeCandidate();

  VoteRequest request;
  request.term = storage_.current_term();
  request.candidate_id = node_id_;
  request.last_log_index = log_storage_->LastIndex();  // 最新日志 index
  request.last_log_term = log_storage_->LastTerm();    // 最新日志 term

  for (const auto& peer_id : GetPeerIds()) {
    VoteResponse rsp = transport_->SendVoteRequest(peer_id, request);
    if (rsp.vote_granted)
      vote_count_++;   // 收集选票
  }
  TryBecomeLeader(result);   // 检查是否达到多数派
}
```

每个 peer 收到请求后，在 `OnRequestVote` 中检查（`raft_node.cc:208-239`）：
- 请求的 term < 自己的 term → 拒绝
- 已经投过其他人 → 拒绝（一票制）
- 请求者的日志不如自己新 → 拒绝（`last_log_term` / `last_log_index` 比较）
- 都通过 → 同意

**⑥ 判定当选（`TryBecomeLeader`）**

```cpp
bool RaftNode::TryBecomeLeader(const ElectionResult& result) {
  size_t total_nodes = cluster_config_.voters.size() + 1;  // 包含自己
  size_t majority = total_nodes / 2 + 1;                   // 多数派门槛
  if (result.votes_received >= majority) {
    BecomeLeader();
    return true;
  }
  return false;
}
```

`BecomeLeader()` 触发 `SetRole(Leader)`：

```cpp
case RaftRole::Leader:
  leader_term_ = storage_.current_term();
  election_timer_.Deactivate();           // 停止选举计时
  StopHeartbeat();
  StartHeartbeat(heartbeat_interval_ms_); // 开始向 follower 发心跳
  break;
```

当选后立即开始广播心跳（`AppendEntries` 的 keep-alive），让其他节点知道选举已经完成。

##### 途径三：接收更高 term 的请求 → 降级为 Follower

即使已经是 Leader，如果收到其他节点发来的更高 term 的请求，自动降级：

```cpp
void RaftNode::BecomeFollower(Term term) {
  DCHECK_GE(term, storage_.current_term());    // 只能升不能降
  storage_.set_current_term(term);              // 更新到新 term
  SetRole(RaftRole::Follower);                  // 降级
}
```

触发场景：
- 收到 **更高 term 的 AppendEntries** → 说明有新的 Leader 当选
- 收到 **更高 term 的 RequestVote** → 说明有任期比自己高的 candidate
- 代码入口：`OnAppendEntries`（`raft_node.cc:326-370`）和 `OnRequestVote`（`raft_node.cc:216-218`）

```cpp
// OnAppendEntries 中（raft_node.cc:338-342）
if (request.term > storage_.current_term()) {
  BecomeFollower(request.term);
}
```

##### 三种途径对比

| 场景 | 初始角色 | 如何成为 Leader | 触发时机 | 代码 |
|------|---------|----------------|---------|------|
| **单节点启动** | Follower | `BootstrapSingleNode` | `Init()` 中直接调用 | `raft_node.cc:184` |
| **多节点：已有 Leader** | Follower | 接收心跳，保持 Follower | 每次收到 AppendEntries | `election_timer_.Reset()` |
| **多节点：Leader 宕机** | Follower → Candidate → Leader | 选举超时 → 投票 → 多数派 | 150-300ms 随机超时 | `raft_node.cc:202-293` |
| **角色冲突** | Leader → Follower | 收到更高 term 的请求 | 任何时刻 | `raft_node.cc:169-173` |

**核心要点**：节点启动后不假设自己是主机还是从机。先当 Follower，通过 Raft 选举自然决定角色。`meta.json` 恢复的 term/voted_for 只回答"上一个任期我投给了谁"，不直接决定当前角色。当前角色由 **是否收到心跳** 和 **选举结果** 动态决定，保证了 **Election Safety**（每个任期最多一个 Leader），不会出现双主（split brain）。

---

### 6.3 WAL 损坏怎么办

`ScanSegment`（`segment_log_storage.cc:109-158`）的处理策略：**遇错即停，保留有效的部分**。

```
WAL 文件内容:
[entry1✓] [entry2✓] [entry3✓] [entry4 部分写] [entry5 数据]

扫描结果:
  entry1, entry2, entry3 → 成功加载
  entry4 → 头不完整或 CRC 失败 → 停止
  entry5 → 被丢弃（在坏记录之后）
```

**原理**：Raft 日志必须连续。entry4 损坏意味着 entry5 的 index 可能也不正确。安全策略是停止在最后一个有效记录，丢弃之后的所有内容。丢失的数据通过 Raft 的 AppendEntries 从 Leader 重新获取。

### 6.4 Snapshot 损坏怎么办

`SnapshotLoader::Load()` 验证三要素：
- `snapshot.meta` 存在且 index > 0, term > 0
- `snapshot.bin` 存在且 magic 头正确 (`0x50414E53`)
- 任意一项失败 → 返回 `Corrupted`

恢复时如果 Snapshot 损坏 → 跳过快照恢复 → 从头 replay 所有 WAL → 如果 WAL 也不够长 → 依赖其他节点的 AppendEntries 同步。

### 6.5 Recovery 如何保证一致性

| 检查点 | 机制 |
|--------|------|
| **WAL 完整性** | CRC32C 逐条校验 |
| **日志连续性** | 单调 index 检查 |
| **Snapshot 完整性** | Magic 头 + meta 文件验证 |
| **apply 进度** | `apply.meta` 持久化 last_applied |
| **Raft 元数据** | meta.json 原子写保证 term/voted_for |
| **WAL 截断安全** | 遇错即停，不从坏处跳过 |

## 7. 完整数据写入流程

以 `SET a 1` 为例：

```
redis-cli: SET a 1
    │
    ▼
1. RESP Parser
   Connection::ParseMultiBulk
   → ParsedCommand{tokens=["SET","a","1"]}
    │
    ▼
2. Raft Commit
   Service::Set → engine_.SubmitCommand()
   ├─ CommandEncoder::Encode → ReplicatedCommand{SET,["a","1"]}
   ├─ role!=Leader? → ERROR
   ├─ LogStorage::Append(LogEntry{term, 0, "SET a 1"})
   │   └── FileLogStorage: writer_.Append (header+crc32 → buf)
   ├─ ReplicateLog → 向 peers 发 AppendEntries
   ├─ AdvanceCommitIndex (多数派检查)
   └─ ApplyCommittedLogs
        └─ state_machine_->ApplyLogEntry
             └─ KvStateMachine::Set → shard_set_->Await → DbSlice 写入
    │
    ▼
3. WAL Flush (调用者控制时机)
   wal_writer_.Flush()
   ├─ fwrite(buf_)
   ├─ fflush(file_)
   └─ fdatasync(fileno)        ← 数据落盘
    │
    ▼
4. AOF Append
   persistence_manager_->RecordCommand(["SET","a","1"])
   ├─ CommandSerializer::Serialize → "*3\r\n$3\r\nSET\r\n..."
   ├─ aof_writer_.Append(resp)
   └─ aof_writer_.Flush()     ← 仅 fwrite+fflush，无 fsync
    │
    ▼
5. Snapshot 触发（异步，后台 fiber）
   每秒检查 last_index - snapshot_index >= 100000?
   ├─ YES → CreateSnapshot()
   │   ├─ barrier_.BeginWrite()     ← 暂停写
   │   ├─ SaveSnapshot(snapshot.bin)
   │   ├─ CompactLogs(index, term)  ← 删旧 WAL
   │   └─ barrier_.EndWrite()       ← 恢复写
   └─ NO  → 继续等待
```

**每一步设计原因**：
- 先 Raft 提交再写 DbSlice：保证只有被 majority 确认的数据才对客户端可见
- WAL 在 Raft commit 时已写入（`FileLogStorage::Append`），但 fsync 由上层控制
- AOF 是额外的兼容层，在 Raft 提交之后补充写入
- Snapshot 是异步的，不阻塞写入路径

## 8. 性能优化

### 8.1 WAL 顺序写优势

WAL 是**纯追加**的，没有随机写。磁盘的顺序写吞吐量远高于随机写（HDD 上可达 100MB/s+ vs 1MB/s）。

本项目中 `FileLogStorage::Append` 就是往 `WalWriter` buf 里追加，Flush 时 `fwrite` 一次写入。没有 seek 操作。

### 8.2 fsync 策略

| 层次 | 策略 | 代价 |
|------|------|------|
| WAL | `fdatasync` per Flush | 每次 ~1ms 磁盘延迟 |
| AOF | `fflush` only | 无磁盘延迟，但 Kill -9 可丢数据 |
| Meta | `fdatasync + rename` per write | 每次 ~1ms，但只写小文件 |
| Snapshot | `fdatasync + rename` at Finalize | 仅在快照创建时，频率很低 |

**为什么没有 group commit（批量提交）**：当前每次 `Flush()` 立即 `fdatasync`，没有将多次写入合并为一次 fsync 的机制。这是性能优化点。

### 8.3 Snapshot 减少恢复时间

- 无 Snapshot：恢复 100 万条 WAL → 每条需反序列化 + 校验 CRC + apply → ~10-30 秒
- 有 Snapshot：加载 snapshot.bin（批量导入）+ 重放 1000 条 WAL → ~1 秒

### 8.4 Log Compaction 降低磁盘占用

- 无 Compaction：WAL 无限增长，百万条 ≈ 几百 MB
- 有 Compaction：Snap 后只保留最近的 WAL，旧段 `unlink` 删除 → 常量级磁盘占用

### 8.5 AOF 对性能影响

当前 AOF 是同步写入（`Flush` 每命令），`fflush` 不算太重，但**每次命令多一次内存拷贝和 RESP 序列化**。如果改为异步 AOF（后台线程定期刷），可减少主路径开销。

### 8.6 Fiber + io_uring

项目的 IO 操作（fwrite、fsync、fdatasync）是同步阻塞调用。虽然项目使用 fiber，但文件 IO 走的是传统 libc stdio，**并未接入 io_uring**。io_uring 在当前项目的主要用处在网络 IO 侧。

如需优化持久化性能，可以将 `WalWriter::Flush()` 的 `fwrite+fdatasync` 改为 io_uring 的异步 `write+fsync`，减少 fiber 阻塞时间。

## 10. 面试重点

### 10.1 第一轮：基础认知

**Q1: 为什么需要 WAL？**
> WAL 是 Raft 共识的基础——日志必须先持久化到磁盘，再 apply 到状态机。这样崩溃重放后状态机与日志一致。如果先 apply 再写 WAL，崩溃时已 apply 但未落盘的数据就会丢失且无法恢复。

**Q2: WAL 和 AOF 有什么区别？**
> WAL 是二进制格式，带 CRC32C 校验，用于 Raft 节点间日志复制，fdatasync 保证落盘。AOF 是 RESP 文本格式，用于 Redis 兼容持久化，fflush 保证写入但无 fsync。两者独立存在，分别服务于共识复制和兼容性。

**Q3: 为什么先写 WAL 再 Apply？**
> WAL-first 是崩溃恢复的基石。如果先 Apply 再写 WAL，崩溃时"已执行但未记录"的状态无法恢复。先写 WAL 再 Apply，崩溃后可以 ReplayUnappliedLogs 重放恢复。

**Q4: Snapshot 为什么不会破坏一致性？**
> SnapshotBarrier 在创建前暂停所有写操作（writing_=true）并等待 in-flight 写完成（readers_→0），此时状态机处于静止状态，导出的是一致的快照。压缩日志时保留 SnapshotAnchor，使 AppendEntries 的 prevLogTerm 检查继续有效。

### 10.2 第二轮：实现细节

**Q5: CRC 为什么只覆盖 payload 不覆盖 header？**
> Header 的损坏通过两种方式检测：① 部分写导致 `fread` 读不到完整的 24 字节（partial header → 停止扫描）；② index 非严格递增（同一个 segment 内 index 必须递增，坏 header 会导致此项检查失败）。CRC 覆盖 payload 解决了 command 数据位翻转/部分写的问题。两项组合覆盖了大部分损坏场景。

**Q6: Log Compaction 为什么安全？**
> Compaction 发生在 Snapshot 创建并落盘之后：① snapshot.bin + snapshot.meta 已 fsync → 数据不会丢；② 只删除快照中已包含的 index 之前的 WAL → 快照未覆盖的日志保留；③ SnapshotAnchor 保留关键 (index, term) → 一致性检查不失效。

**Q7: fsync 有哪些策略？各自的 trade-off？**
> 项目有三种策略：① `fdatasync`（WAL、meta）：数据落盘，不落元数据（mtime），比 fsync 少一次磁头移动；② `fflush` only（AOF）：只写入内核缓冲区，进程崩溃不丢但 Kill -9 可能丢；③ `fflush + fdatasync + rename`（meta/snapshot 原子替换）：写临时文件→刷盘→原子 rename，保证要么全有要么全无。

**Q8: Kill -9 后如何恢复？**
> ① meta.json（fsync 的）恢复 term/voted_for；② apply.meta（fsync 的）恢复 last_applied；③ snapshot.bin 存在则 LoadSnapshot 恢复全量；④ SegmentLogStorage::Open 扫描 WAL segments，逐条 CRC 校验，遇错停止；⑤ ReplayUnappliedLogs 从 last_applied+1 重放到崩溃前的 commit_index；⑥ AOF ReplayAof 额外重放 RESP 命令。

### 10.3 第三轮：深挖

**Q9: Snapshot 和 WAL 如何配合？恢复先用哪个？为什么？**
> 先 Snapshot 后 WAL。Snapshot 是"全量存档"（覆盖 index 1~100000），加载快全量；WAL 是"增量流水"（index 100001~101000）。恢复顺序：LoadSnapshot → 恢复全量 → 再 ReplayUnappliedLogs（只重放快照后的增量）。如果反过来（先 WAL 再 Snapshot），先重放全部日志再把快照覆盖上去，快照后的增量就丢了。

**Q10: WAL 损坏怎么办？能跳过损坏记录继续吗？**
> 不能跳过。`ScanSegment` 遇任何异常（partial header、CRC 失败、非单调 index）都立即停止扫描当前及后续 segment。因为 Raft 日志必须连续无空洞——如果跳过 index 500 的坏记录，index 501 的位置信息也不可信。安全策略是停止在最后一个有效位，依赖 Raft 的 AppendEntries 从 Leader 重新拉取后续数据。

**Q11: AOF 和 WAL 会不会重复？恢复时怎么处理？**
> 会重复。WAL 和 AOF 都记录了每一条写命令。恢复时两者独立执行：WAL 重放走 `ReplayUnappliedLogs` → `ApplyLogEntry`；AOF 重放走 `ReplayAof` → `DispatchCommand`。AOF 在恢复时设 `replay_mode_=true`，重新 replay 命令时由于状态机操作是幂等的（SET 覆盖、DEL 不影响），正确性不受影响，但恢复时间翻倍。

**Q12: 最大的持久化相关局限是什么？**
> ① AOF 无 fsync，Kill -9 可能丢最后一条 AOF 记录；② AOF 无 rewrite，文件无限增长；③ WAL 无 group commit，每次 Flush 单独 fdatasync；④ AOF 的 Load() 硬编码文件名，忽略 Open() 传入的路径（已知 bug）；⑤ 文件 IO 用 libc stdio 同步调用，未接 io_uring。

## 11. 最终总结

### ① 一分钟介绍
> "我的持久化分三层：WAL（二进制分段 + CRC32C + fdatasync）负责 Raft 共识日志的持久化与恢复；AOF（RESP 文本）提供 Redis 兼容的命令日志；Snapshot 通过 SnapshotBarrier 保证一致视图的全量快照，配合 Log Compaction 删除旧 WAL 段。恢复按 Snapshot → WAL → AOF 顺序。"

### ② 三分钟介绍
> "WAL 采用二进制 RecordHeader(index/term/size/crc32) + command 格式，按 64MB 分段，Append 写入内存 buf，Flush 时 fwrite+fflush+fdatasync 落盘。恢复时 SegmentLogStorage::Open 扫描所有 segment_N.log，逐条 CRC32C 校验，遇错即停。AOF 是独立的 RESP 文本持久化层，CommandSerializer 把每次写命令转为 RESP 格式追加到 appendonly.aof，提供 Redis 工具链兼容性。Snapshot 通过 RaftSnapshotManager 的后台 fiber 触发（日志超出 10 万条），创建时 SnapshotBarrier 暂停写导出全量，完成后 CompactLogs 设 SnapshotAnchor + 删旧 WAL segments。恢复先加载全量快照，再 ReplayUnappliedLogs 重放增量，最后 ReplayAof 补充。"

### ③ 五分钟介绍
