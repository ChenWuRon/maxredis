# 第十部分：不同职级的讲法（校招 → P8）

> 同一项目，不同讲法。关键词："项目深度展示 = 职级"，讲错了等于自曝天花板。

## 校招 / 实习转正
- **定位**：证明"能独立吃掉一个有难度的系统"。
- **讲**：15s 开场 → Raft 共识 + 崩溃恢复一条具体链路（图 8 提交、WAL 撕裂尾、apply.meta 顺序三件套任选）→ 主动讲 Q16 Figure 8 的崩溃序列 → 说"我读了源码才讲得出这个细节"。
- **禁止**：讲架构图十张全铺开、讲扩展路线图（那是 P6+ 的话题）。

## P5（初级）
- **定位**：证明"我能闭环交付功能"。
- **讲**：30s 开场 + 一个完整特性从设计到落地（如：ReadIndex 的三阶段 + lease 续期证据 + 5s 超时缺陷的自曝）→ 引用文件:行号（证明是自己写的）→ 讲一个测试案例（PartitionedTransport 怎么模拟分区）。
- **禁**：讲"性能优化方向"而不讲"已兑现的优化"。

## P6（中级）——重点准备
- **定位**：证明"我能做技术决策 + 影响他人"。
- **讲**：why 故事——为什么选 fiber 弃线程池/回调、为什么 WAL 当唯一真相、为什么事件驱动 lease 而非定时租约；每个决策给 Compare & Falsify（我当时评估过 X，放弃因为 Y，证据行号）。
- **讲技术债台账**：20 条里挑 3 条最狠的自曝（快照未接线、AOF 破碎、5s 超时返回），并当场给"我已排期的修复计划"——**主动自曝 + 修复计划 = P6 的成熟度信号**。

## P7（高级）
- **定位**：证明"我能定架构、能指挥攻防"。
- **讲**：一致性/可用性/延迟三轴权衡全图——lease 缩短换读延迟、CheckQuorum 600ms 换脑裂收敛、AOF 双写换兼容性，每条都是"我拍板的 trade-off"而非"别人定的"。
- **讲横切**：多 group 分片扩展设计评审（交出设计而非现状）。
- **禁**：把 L4 缺陷当"历史遗留"讲——要当"我知道它为什么、我排期修它"讲。

## P8+（架构师）
- **定位**：证明"我能带一个系统的长期演进"。
- **讲**：技术债台账 20→6 的推演（哪些故意不修、哪些必须修、修的顺序为什么）→ 4 周路线图的投资回报论证 → 讲"哪些债是我故意留的"（如 FileLogStorage 留作测试快速迭代）。
- **讲生态**：benchmark 口径、CI 门禁、可复现性——工程效能也是架构。

# 第十一部分：3 / 5 / 10 分钟背诵稿（口语逐字）

> 每句都能背。3 分钟版用时最短，5 分钟加源码细节，10 分钟加故障案例与本答疑。

## 3 分钟版（电梯稿，约 450 字）
"我做的是一个基于 Raft 的分布式 Redis 兼容存储，C++，替代单机 Redis 的可用性短板。核心思路：所有写操作先请求 leader，作为日志条目追加进 WAL，复制到多数派并经受 Raft 的提交规则裁决，再应用到状态机；所有节点按同一总序应用状态，所以任一节点崩溃，集群在几百毫秒内选出新 leader 继续服务，已提交的数据零丢失。

关键设计三个：
第一，一致性。读路径用 ReadIndex 加事件驱动租约——只有当多数派确认我是 leader 我才直接本地读，否则走一次确认 RPC，保证线性化。
第二，持久化。WAL 是唯一真相，先刷 WAL 再刷 apply.meta，崩溃恢复宁可重复重放幂等命令，绝不跳过已应用条目；WAL 的撕裂尾在恢复时被严格校验丢弃。
第三，性能。基于 io_uring 和 fiber 的 Proactor 模型，每连接一个 fiber，阻塞式 API 背后是内核异步轮询，单连接无盘路径实测 4 万 QPS、P99 54 微秒。

我自己实现了完整的 Raft 协议：选举、日志复制、Figure 8 提交限制、联合共识成员变更、leader 转移、快照与日志压缩，270 个测试覆盖 18 个目标。

我也清楚自己的哪些地方还没到位：快照接收链路还没有在生产接线、memcached 存储路径有断链、线性化读有 5 秒超时缺陷——这些我都有排期的修复计划。"

## 5 分钟版（+ 源码细节，约 900 字）
（3 分钟版全部 + 以下三段替换为细节叙述）

"讲三个最容易出问题的协议细节，我都是对照源码答案：

**Figure 8。** 所有 Raft 提交都基于多数派，但旧 term 的条目不能直接提交——因为更早 term 的 leader 可能覆盖它。我代码里 commit 位置是 raft_node.cc 的第 1449 行，取日志索引排序的多数派值；但只有当前 term 的条目能直接推进提交，旧 term 条目只能靠它上方的当前 term 条目被提交时顺带提交。这个判定在 1472 到 1479 行。这就是 Raft 论文第 5.4.2 节的完整落地。

**崩溃恢复的顺序。** WAL 先落盘，apply.meta 后落盘，方向是严格的——如果反了，恢复时会以为条目已应用而跳过，那就丢了已提交数据；正确的方向即使 apply.meta 落后，重放的也只是幂等命令，最多重复无害。这个顺序在两处代码里写成硬约束。

**租约的可信边界。** 我的租约只在两个时刻续期：多数派心跳被确认时，和 ReadIndex 确认时——续期权和多数派是一体的，这是它可信的根本。但租约有个已知边界：进程被暂停会伪造时间，所以我还配了 600 毫秒的 CheckQuorum，多数派长期失联就强制下台，保证分区后旧 leader 不会继续卖读。"

# 第十二部分：红线清单（关于诚实的一切底线）

> 面试的本质是"信得过"。以下任何一条破了，前功尽弃。

## 绝不能撒谎（违反 = 淘汰）
1. 性能数字：必须带口径（单连接/无盘/2 核 VM），不主动夸大，实测 40K/P99 54us；63 万 pipeline 只提"自测数字, 无 harness 可复现"。
2. 功能完整度：memcached 存储路径断链（L4）必须主动承认。
3. 快照：接收侧未接线，落后节点只能日志追赶（L4）必须主动承认。
4. 多 group：框架在、测试在、生产未接线（L2）——"支持分片"的表述必须降级为"框架与测试就绪，改造已排期"。
5. 测试：ctest 大盘陈旧、raft_cluster_test 声明未构建——"270 用例全绿"只说"我实测的三套核心测试全绿"。
6. INFO 假字段：被问到版本/内存直接说"为了兼容占位, 真实统计在路上"。
7. AOF：无 fsync + 漏 EXPIRE——不能拿"Redis 兼容"当卖点提。

## 必须承认的（承认 = 加分项）
1. 先承认再解释："这里我有三个已知缺陷，我讲一个我不满意的的实现——"
2. 讲缺陷时给行号（证明读过源码）再给修复排期（证明有掌控）。
3. "文档和代码不一致"的主动核对（Q5 选举区间）——让面试官看到诚实核对习惯。

## 被逼问时的转移路线（不撒谎也不冷场）
- "为什么不用 etcd" → 答比较后说"如果只做共识底座我会推荐 etcd"再转"我做的是存储+共识+网络的闭环"。
- "270 测试真的全绿？" → "我实测 core 三套全绿；全大盘有陈旧注册，这正是我 Week4 收口项"。
- "你的性能是不是假的？" → "口径我讲清楚，数字可以复现，harness 在排期"。
- "INFO 7.2.0 是假的？" → "是。为了老客户端版本门禁兼容，metrics 是占位符，我的修复计划是版本按真实特性表配置化"。
