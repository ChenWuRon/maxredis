# 第六部分：20 个压力面问题（含追问与反制）

> 每问结构：主问 → 追问 → 标准反制（把追问引导回自己的源码事实）。所有答法遵循诚实分级原则。

**P1：为什么不用 etcd / 直接用 braft / jGroups？**（自研 vs 成熟）
- 答：用的场景差异——etcd 是"给别的系统当共识底座"，而 maxredis 的诉求是"存储、共识、网络模型在一个进程里闭环"（写路径零序列化、fiber 栈内直接 commit）。自研获三件事：Nakama 全链路可控（快照 64KB 分块、WAL 分段、间隔 fsync 批量）、内核复用（io_uring 连接面 + 电力学触发器）、以及一共 90M 行的总账审计能力。
- 追问：那不是重造轮子吗？
- 反制："轮子重造"要看语义粒度——Raft 协议实现我们有现成测试网 270 用例背书；真正自研的是"fiber 语义 + 单写者 + 一致性路径与 io_uring 的焊接"，etcd 给不了这个焊接。

**P2：性能数字怎么来的，能复现吗？**（信任攻击）
- 答：诚实分层——40K QPS/P99 54us/63 万 pipeline 都来自 docs/存储引擎架构面试准备.md 的自测：2 核 VM、单连接、无 raft_dir（无 WAL fsync）。**没有可复现的 benchmark 脚手架**，这是当前工程债 P3。追问时主动说"数字口径是单连接无盘路径，我注明过；生产开全 fsync 会掉到磁盘同步上限"。
- 追问：那你这数字是不是假的？
- 反制：不是假，是口径窄。我会当场区分三档：纯内存路径（40K）、加 Raft 条目复制不开盘（约 8K）、全持久化（受 fdatasync 限制）——每个数字我都能说出它的代码位置。

**P3：为什么用 mutex 锁又不是无锁？**（并发模型攻击）
- 答：锁的粒度是"微秒级临界段 + fiber 协作调度"：锁内绝不 sleep/IO（raft_node.cc:1062-1080 锁内只做状态操作），等待者是 fiber 让出而非线程忙等。真正重要的对称性是 shard 线程数 = proactor 数 - 1（main_service.cc:90），横向并发归 fiber 与多 proactor，互斥只保护"同写者 + 状态一致性"。
- 追问：那锁竞争怎么办？
- 反制：竞争只发生在"多 fiber 同时进出临界段的一瞬"（微秒级），吞吐瓶颈不在锁在 fsync 与网络；真要降竞争方向是 per-cpu 队列拆分。

**P4：为什么不用线程池 + 回调？**（模型攻击）
- 答：三方面差距——a) 线程池 U 一个任务 = 内核上下文切换 ~1-2us，fiber 切换 ~50-100ns；b) 回调的反控制流让"连接×状态机×重试"不可调试，fiber 保留同步栈（断点、调用栈、内存视图是自然形态）；c) 背压天然——FiberQueue 满则生产方阻塞（engine_shard_set.cc:19，kQueueLen=64），线程池满则要么丢任务要么膨胀内存。项目在 dragonfly_connection.cc:107 就有"每连接一 fiber"的注释立论。
- 追问：fiber 的栈切换代价具体多少？
- 反制：ucontext/jump -fiber 语义约 50-100ns，且只在"确实阻塞"时发生；可论证：1 万连接 × 每秒 10 次阻塞切换 = 每秒 10 万次切换 × 100ns = 10ms CPU，总开销 1 核的 1%。

**P5：为什么不用 Boost.Asio / libuv？**（框架攻击）
- a) Asio 是"回调 + 线程池"模型，我们的阻塞语义要自己包一层协程适配；b) Asio 无内置 fiber 调度器，io_uring 支持是半成品；c) libuv 网络模型同样回调化。真正名符其实的利基点：**helio 是"Proactor + fiber"一体框架，连接建立→读→写→对端关闭全在 fiber 同步栈里**，出错路径（parser_error、close）是线性代码不是异步回调迷宫。
- 追问：Asio 也有 await 支持？
- 反制：那是 C++20 协程的 `co_await`，proactor 与协程协作要自己写 awaitable 适配——等于把框架的同步模型缺点买回来再自己补，违背"选型买什么"的原则。

**P6：为什么不用 RocksDB/LevelDB 做存储？**（存储攻击）
- 答：语义差距——RocksDB 是 KV 引擎但**没有副本语义**，还带 WAL/SST 自己的崩溃模型，与我们"WAL=共识日志=持久化真相"的模型冲突；我们把"持久化"完全交给 Raft WAL（FileLogStorage/SegmentLogStorage），内存态是唯一真相、磁盘是镜像。另一个理由：单写者 + 全内存热路径下，LSM 的写放大是纯负债。
- 追问：那你的内存能做多大？
- 反制：实话——当前全内存（未实现磁盘表），内存就是上限；设计纲领是"内存做主、WAL 做持久化、快照做压缩"，磁盘存储是 roadmap 的 P2 项（应急区内存淘汰）。

**P7：为什么不用 gRPC 做节点通信？**（协议攻击）
- 答：三句——a) Raft RPC 的语义是"帧 + CRC + seq + 超时重试"，gRPC 的 HTTP/2 流式 + 元数据在 40 字节/条的心跳场景是 5 倍膨胀；b) gRPC 线程模型是线程池回调，我们节点通信要进 leader 的 fiber 栈（心跳 fiber 循环 raft_node.cc:676-808）；c) 一个 2 节点心跳 = 每秒 20 个 RPC × 20 字节帧，gRPC 的握手/流保活成本纯浪费。
- 追问：不做二进制协议容易错吧？
- 反制：我们有帧 CRC + seq + 断线重建三重防护（tcp_transport.cc:204-216），测试里 PacketizedTransport 专门嘲讽过帧错位（差距在进程内测试没覆盖 TCP 层, P0 债里认了）。

**P8：为什么 Raft 不用领导者租约模型（Lease-based lease）的标准实现？**（协议攻击）
- 答：标准实现 = 定时器租约（防移领导者）；本项目 = **事件驱动租约**：仅当"多数派 ACK 心跳 / ReadIndex quorum 确认"（raft_node.cc:774-778, :917-918）才续期，leases 永不凭空续——谁碰它必须有新鲜证据。代价是"进程暂停伪造时间"要靠 600ms CheckQuorum 兜底（:779-783）。
- 追问：那被暂停 500ms 会发生什么？
- 反制：lease 过期 → 读走慢路径 → quorum 确认失败 → 拒绝读；正确而非降级。

**P9：多写者并发写会怎样？**（并发攻击）
- 答：写路径是**单写者**（leader），并发写 = 多个客户端 fiber 在 leader 上排队提交，各自绝版 EntrySubmit 后经"锁内捕获一波→锁外批量复制→锁内推进"三阶段（raft_node.cc:1217-1260 区域）。同一个 key 的并发写由日志秩序天然串行化——客户端看到的是总序,不是交错。
- 追问：那不是丢了并行度吗？
- 反制：Raft 写本来就是全序的（State Machine Safety 要求所有节点同序 apply），单写者没有丢并行度，丢的是"多 leader 并行写"——那才是语义破产。

**P10：客户端扩容怎么做？（读多写多）**（扩展攻击）
- 答：读 = 任意节点（follower 直接 kLocal 读/leader 走 ReadIndex），加只读节点只需加 follower；写 = 只能 leader。真正的写扩展 = 分片（HashSlot % num_groups，shard_router.h）+ 每分片独立 Raft 组（框架与测试就绪，接线 P2 债）。当前诚实声明：单组写吞吐上限 = 单写者 + 单 fsync 流水。

**P11：快照为什么 64KB 一块不是一条？**（细节攻击）
- 答：三个权衡——a) 64KB = 4 页页缓存友好；b) 分块让慢网络连接上的断点续传成为可能（未来做分块重传的粒度）；c) 块 CRC 校验在接收侧粒度合理（snapshot_receiver.cc:76-101 写 tmp 后整文件校验rename）。坦白：断点续传未实现，这只是"块"不是为了续传做的。

**P12：日志压缩了怎么恢复？**（协议攻击）
- 答：三段式——a) 快照把"快照点之前的日志"压缩掉（CompactLogs 后 WalIndex 清前缀）；b) GetTerm 走 snapshot anchor（segment_log_storage.cc:244-254）；c) 恢复 = load snapshot + apply.meta 后重放 WAL（raft_storage.cc / raft_node.cc:1599-1660 区域）。三件套配合，压缩不破坏任何一致性检查（prev 检查/投票的 GetTerm 都过了）。
- 追问：anchor 后空日志还能恢复吗？
- 反制：能——anchor 只是"索引压缩"，快照本身就是完整状态，空日志 = 直接应用快照 + 无增量。

**P13：为什么 commit index 不能是"收到我就提交"？**（协议攻击）
- 答：收到 ≠ 持久化 ≠ 多数派 —— commit 的两个前提：a) 该条目**已复制到多数派**（否则下个 leader 可能没它）；b) **当前 term 有提交权**（Figure 8，Q10/Q16）。所以"收到即提交"会违反 State Machine Safety（x=3 案例）。

**P14：Raft 文件里为什么有 128 批量上限？**（实现攻击）
- 答：三个理由——a) 单个 AppendEntries 帧有长度上限？其实真正的理由：控制单次 RPC 的磁盘写入/网络占用与时延；b) 让"慢 peer 的退避重试"粒度可控（8 轮 × 128 = 最多 1024 条/eer）；c) 与 apply.meta 每批 128 条 flush 对齐（raft_node.cc:1623-1631），一条 RPC 恰好一批日志的粒度。不是拍脑袋。

**P15：为什么你们的 SegmentLogStorage 和生产 FileLogStorage 并存？**（打磨攻击）
- 答：诚实——历史包袱：FileLogStorage 是早期单文件实现（现在仅测试在用，因为快：无段/索引层），SegmentLogStorage 是 10 万条/2GB 级规模选型（分段压缩 + WalIndex 索引）。并存 = 语义分叉风险（L2 认可的债），我已在技术债表 P3 里排"推动全部迁移 Segment"。
- 追问：那为什么不直接删掉一个？
- 反制：FileLogStorage 是 raft_node_test 的快速迭代对象（270 用例的主要 runner），删它会失去回归速度——正确顺序是先让 Segment 全量跑同套测试再删。

**P16：你们 memcached 协议支持完整吗？**（功能攻击）
- 答：诚实完整版——set/add/replace 等存储命令的解析器写了（memcache_parser.cc），**但存储路径在生产是断的**：ConsumeInput 只消化了命令行（dragonfly_connection.cc:459），Value 行没进"缓存待处理"结构，DispatchMC 的 store 分支实际进不来（:456 恒 false）。**这是 L4 级实锤缺陷**，我第一周就会接：把 value 进内存 → 补 kQueue 里 kos 结构 → 补测试。
- 追问：所以 memcached 是假的？
- 反制：get 类的读路径能走（回复了 key 值不存在路径）；但写路径确实断——所以我主动说，而不是等你测出来。

**P17：读请求能走 follower 吗？**（一致性攻击）
- 答：官方语义 + 项目实践——项目里 GET 的默认模式其实是 kLocal（main_service.cc:607 直读）；要线性化读必须 `--linearizable_read=true` 走 ReadIndex。所以"follower 能读"与"follower 读得对"是两个问题——follower 读无线性化保证（一致级别自选）。
- 追问：那 Redis 客户端默认怎么办？
- 反制：默认 kLocal 是为了代理读性能；真实分布式系统的做法永远是"模式可配置 + 默认告诉用户语义"（我们是默认弱、可选强，文档已注明）。

**P18：你的 RELOAD / 快照校验有多可靠？**（持久化攻击）
- 答：两层诚实——a) 快照加载只验 4 字节 magic（snapshot_loader.cc:48-63），表头/大小/内容无校验（L4）；b) 快照发送端短读未验证（snapshot_sender.cc:53-58）。修复已在路线图（Week2 参数化 + Week3 快照 CRC）。不会狡辩，直接给修复。

**P19：为什么 INFO 的 redis_version 是 7.2.0？**（诚信攻击）
- 答：是为了兼容老客户端对版本号的检查（大版本门禁），真实特性是"基于 Raft 的分布式一致性"（所以用 role=master/slave 表示 leader/follower）。**明说**：这是伪报（metrics 里的 used_memory:0 也是），技术债 P3，方向是"版本号按真实特性表配置化"。
- 追问：那 redis_version 之外还有哪些假？
- 反制：used_memory、expires、瞬时 OPS、CPU 均为 0 占位符；真实的数据（连接数、keys 数、命中率、raft 段数）我去 INFO 里指给你。

**P20：为什么 does leader lease 比其他实现短？**（协议攻击）
- 答：证据密度差异——我们 lease 是"事件驱动"（每心跳 ACK 续 100ms 已足够，因为 50ms 心跳 + 100ms 超时 = 每轮至少一条新鲜证据）；etcd 的标准租约是"固定时长"，我们的更短 = 更保守，代价是要更频繁的多数派接触（心跳永远在跑）。
- 追问：可是 100ms 太短了吧，抖动就丢租约？
- 反制：丢租约 ≠ 错误——丢租约只是"读从快路径降级到慢路径"，最多一读一慢；而丢租约后的读正确性由 ReadIndex 慢路径兜底，读永远不会错,只是可能慢。（这个框架思维很加分。）

# 第七部分：8 个真实故障排查案例（Star 面试法全演练）

> 每案：现象 → 排查 → 根因 → 修复 → 复盘。按"STAR 面试"口径组织：Situation-Task-Action-Result。

## 案例 1：Follower 持续落后，写延迟飙升（L2 实测）
- **现象**：3 节点集群，一个 follower 的写延迟偶尔 300ms+，leader 日志堆积。
- **排查**：先看 leader 日志——心跳 catch-up 触发 ReplicateLog(false)（raft_node.cc:805-806）；看 follower 的 next 回退：快速回退公式 backoff=min(next-1, peer_last+1)（:1406-1417）一次跳 8000+ 条，但每轮 128 条 → 落后 10 万条要 ~800 轮，一轮一个 RTT——线性放大。
- **根因**：没有快照兜底路径（S: InstallSnapshot 收侧未接线 L4）+ 批量上限固定 128。
- **修复**：临时调高 128→512 观察；根修 = 接线 SnapshotReceiver + 快照边界 log_gap 参数化。
- **复盘**：落到"配置文件 + 路由"，这类案例就是面试讲"为什么 log_gap/接线优先级最高"的现成材料。

## 案例 2：SIGSEGV（内存错误）
- **现象**：某次压测中进程崩溃，core dump 在 raft_node.cc 附近。
- **排查**：gdb bt 看栈——崩溃在 EntrySubmit→SubmitEntry 路径（raft_node.cc:1217-1260 区域）；再 valgrind/ASAN：**超时后的 double-free 是怀疑主线**——客户端 fiber 超时重试时旧 EntrySubmit 的 ctx 已被回收，第二次还在用（RaftNode 有"expired ctx"检查但超时窗口内可能遗漏）。
- **根因**：结论 A：超时重试破坏 ctx 生命周期；B：锁内持 fiber 生命周期对象的引用。
- **修复**：统一 ctx 生命周期 = 与 RaftNode 同周期创建/销毁 + 锁内绝不借出引用；ASAN 常驻测试 CI（现未开，P2）。
- **复盘**：教训是"fiber 并发 + 异步超时 = 双重生命周期陷阱"。

## 案例 3：kill -9 后重启，日志丢失
- **现象**：raft_dir 模式 kill -9，重启后 leader 丢失最后 ~1 秒日志，客户端有未 ACK 请求。
- **排查**：按 Q90 分层：kill -9 = page cache 还在（interval=0 默认 fsync 应无丢）；丢说明是 interval 模式（fsync_interval_ms>0）或**fsync 返回未检查**（raft_storage.cc:133-157 L4）。
- **根因**：模式相关 + 检查缺失——interval 窗口内的写对掉电不设防；fsync 失败被忽略会扩大"以为落盘"的窗口。
- **修复**：线上默认全 fsync；interval 模式日志明确"至少丢 interval 窗口"；fsync 返回检查（Week2 P0 项）。
- **复盘**：配置语义必须写进 flag 文档（main_service.cc:45-49 已写）——面试直接引用这句注释。

## 案例 4：网络分区——旧 leader 还在卖读
- **现象**：两台节点被路由隔离，旧 leader 对客户端的读请求仍返回 200。
- **排查**：为什么没被拒绝——lease 检查在 leader 侧（:862-866），分区后 100ms 内 lease 过期 → 应该走慢路径；慢路径 ReadIndex RPC 超时 150ms → 返回 not leader（:896-899）→ 客户端收到 404/READONLY。但 CheckQuorum 600ms 内旧 leader 不自杀，窗口存在。
- **根因**：语义上"lease 失效"与"自动下台"是两个握手的间隙；600ms 内旧 leader 仍能服务"快路径读"？——真相距：lease 100ms 会先过期，所以最多 100ms 裂缝（读会降级而不是错）。
- **修复**：可靠 = 跟随者 ReadIndex 的确认是最终裁决，旧 leader 无论 lease 何时，慢路径失败必然拒读。真正该加的是第三方仲裁/或缩短 CheckQuorum。
- **复盘**：答案是"有窗但不产生错误值"，这类案例要让面试官看到你"先定性（正确性）再定量（窗口大小）"。

## 案例 5：TIME_WAIT 大量堆积
- **现象**：连接断开后 TIME_WAIT 端口高达数万，新连接失败。
- **排查**：netstat 看端口状态；查代码——每次写失败/对端关闭都 Close（dragonfly_connection.cc:289-303 错误路径），Raft RPC 的断线重建（tcp_transport.cc:204-216）也频繁重连 → TIME_WAIT 由主动关闭方积累。
- **根因**：大量短连接 + 主动关闭方缺乏端口复用/SO_LINGER 配置。
- **修复**：a) Raft RPC 保持长连接（心跳复用同一连接，已做）；b) 客户端侧 `tcp_tw_reuse=1` 或调高本地端口范围；c) 连接池化。
- **复盘**：这是"底层基础设施问题用应用层参数解决"的经典现场。

## 案例 6：WAL 半写在恢复时被发现
- **现象**：恢复日志报"torn tail"警告，某条已 ACK 的写丢失。
- **排查**：palantir——先分叉：ACK 发生在 fsync 后（Q33 论证）→ 已 ACK 的不能丢；所以丢的是"未 ACK 的尾巴"（客户端收到的 200 是在 fsync 之后，这个区间 TCP 已把数据交给内核）。torn tail 检测 = ScanSegment 的 CRC/非单调 check（segment_log_storage.cc:145-182）且丢弃安全。
- **根因**：语义完整——恢复对"半写"的唯一的合法解释就是丢弃，且丢弃的必然不是已 ACK 的。
- **修复**：不需要修复协议；需要的是测试覆盖"文件尾部恰好在记录中间"（已有案例，但没进 CI 回归）。
- **复盘**：把"为什么可以安全丢弃"讲清楚 = 讲一遍 fsync-ACK 序，这就是 Q31/33 的联合考点。

## 案例 7：Lease 长时间不续，读全部变慢
- **现象**：压测中所有读 P99 从 54us 涨到 200ms。
- **排查**：看 lease 每次续期在"心跳 ACK/ReadIndex quorum"（:774-778/:917-918），心跳 50ms 一次应该每 100ms 续——说明**某 peer 心跳长期不 ACK**（peer_hb_ok_ 全 false？外循环 8 轮 catch-up 全失败）。
- **根因**：单 peer 分区——lease 续期需要多数派 ACK，1/3 节点丢 → 2/3 仍多数 → 续期应正常；真相是 peer 的 ACK 被"帧校验失败断连重组"拖慢（tcp_transport CRC 失败立即关闭）。
- **修复**：断线重建后第一轮心跳为空帧（不带日志）→ 快速恢复；把"心跳快路径"从"RPC 慢路径"剥离（并行心跳, 技术债 P1）。
- **复盘**：给面试官的信号是"我能把 54us 涨到 200ms 的链路一英尺一英尺挖到底"。

## 案例 8：心跳风暴（选举抖动）
- **现象**：re-image 后集群 40 秒内 5 次 leader 切换。
- **排查**：日志看换届原因全是"check election timeout"；查 term：term 每 2-3 秒 +1，说明总有一个节点无法联系多数派—查 tcp 连接：某 peer 的 TCP 帧 CRC 校验连续失败 → 每轮重连（tcp_transport.cc:204-216 帧错误即断）→ 心跳 RPC 串行 + 超时 150ms × 2 peers = 最坏 300ms/轮 → 选举定时器 300ms 被碰巧跳过？不，300ms 下限 < 300ms RPC → 决定性：选举下限 300ms < RPC 上限 300ms，抖动窗口存在（Q88 是同一案例）。
- **根因**：心跳串行发送的时延总和逼近选举下限（raft_node.cc:697-699 注释明说旧实现 1s 超时导致选举抖震）。
- **修复**：并行心跳（技术债 P1 核心项）+ 心跳 RPC 不携带日志（必要时分离 log 同步路径）；临时止血 = 调大选举下限。
- **复盘**：这是"参数之间的数学关系引发的系统性故障"的最好教材——50ms 心跳、300ms 选举、150ms RPC 超时三个数的算术关系，面试直接背。
