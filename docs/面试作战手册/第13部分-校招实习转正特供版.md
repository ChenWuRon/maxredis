## 13.2 逐字稿（15s / 1min / 3min）

### 15 秒版
"我读完了整个 Raft 共识模块的源码，讲得出 Figure 8 提交限制和崩溃恢复的细节，也在代码里发现并排期了三个真实缺陷。"

### 1 分钟版（面试开场自我介绍用）
"我深入研究了项目里的分布式 Redis 存储：它用 C++ 从零实现了 Raft 共识，跑在自研的 fiber 协程框架上。我最熟的部分是三块：第一，Raft 的日志复制与提交——commit 判定在 raft_node.cc 的 1449 行，多数派排序决定提交位置；第二，崩溃恢复——WAL 先落盘、apply.meta 后落盘这个顺序是硬约束，恢复宁可重放幂等命令也不能跳过已应用条目；第三，我读了全部源码之后发现这里还有三个没做完的地方，快照接收链路没接线、memcached 存储路径是断的、线性化读有个 5 秒超时缺陷——我今天最想讲的就是我发现的这些。"

### 3 分钟版（主菜，项目深挖环节）
"我选的题目是 Raft 的日志复制与提交，讲三个层次。

**第一个层次：提交规则。** Raft 提交看多数派，但有个反直觉的细节：只有当前 term 的条目能直接推进 commit，旧 term 的条目必须等它头上的当前 term 条目被提交时顺带提交。代码在 raft_node.cc 的 1449 行到 1479 行。为什么必须这样？因为 Figure 8：一个旧 term 的条目即使已经有多数派副本，也可能被后来的 leader 覆盖，直接提交它就违反了状态机安全——两个节点可能对同一个 key 应用不同的值。

**第二个层次：崩溃恢复。** 磁盘上有两份状态：WAL 和 apply.meta。顺序必须是先 flush WAL、再 flush apply.meta，这是硬约束。如果反了：恢复时以为条目已应用而跳过，已经提交的数据就丢了；而正确顺序下最坏情况只是 apply.meta 落后、重放幂等命令，最多无害重复。所以 SET 这类命令天然幂等是必须的，代码注释里都写了。

**第三个层次：我发现的缺陷。** 第一，快照接收侧没接线——代码里 OnInstallSnapshot 入口有检查，但生产路径没有任何地方构造接收器，落后节点只能靠日志追赶；第二，memcached 的存储命令解析器写了，但 value 根本没进内存，DispatchMC 不会执行；第三，线性化读 5 秒超时后照常返回，可能给客户端陈旧值。这三个我都能指出具体文件行号。如果让我来修，第一周就接快照链路，因为它把整个协议的能力补齐。"

## 13.5 校招红线（额外 10 条）

1. **答不出就说"这个我没读到，但我可以讲讲我读过的相邻部分"**——比硬编强十倍。
2. **不说"我实现了 X"**——除非是你真的写的；统一口径"我读源码验证了 / 我梳理了"。
3. **不许背手册痕迹**：行号要随口说，别像在念稿；被人反问行号要去得对。
4. **性能数字必须带头衔**："单连接、无盘、2 核虚拟机"，否则就是吹。
5. **别贬低 redis/etcd**——"他们解决了 X 而我做的是 Y"永远比"他们的 X 不行"安全。
6. **维护者提问用"我会去看源码确认"结尾**——校招最加分句。
7. **别主动讲 63 万 pipeline**——大概率引火烧身（无 harness 可复现），被问才讲口径。
8. **被要求画架构图**：画 write path 单条链路（client→leader→WAL→复制→apply）就行，比十张图全铺开强。
9. **被问"最大的项目复杂度"**：答 Raft 提交规则的三个反直觉点，而不是"代码量"。
10. **结尾固定问句**（让面试官记住你）："如果我要把快照接收链路接上线，你们更看重先接哪一步？"——展示已经在想动手。
